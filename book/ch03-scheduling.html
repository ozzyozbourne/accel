Chapter 3

Scheduling and fusion

A tinygrad expression builds a lazy graph and nothing runs. When you call .realize(), the scheduler turns that graph into a list of kernels. It has to decide which intermediate values get written to memory and which are recomputed inside their consumers. This chapter follows every scheduler pass in order, explains rangeify, the step that turns whole-tensor ops into loops over index variables, and uses it to explain why ((a*b+c).relu()*2) is one kernel while softmax is three, and what PyTorch's Inductor does differently.

Why fusion is the first optimization

On a GPU, an elementwise op on a large tensor does almost no arithmetic per byte it touches. a*b on two 1024×1024 float32 tensors reads 8 MiB and writes 4 MiB to do one million multiplies. The SMs finish the math long before memory can deliver the operands. Such an op is memory-bound, and its run time is set by the bytes it moves.

Run ((a*b + c).relu() * 2.0) one op at a time, as PyTorch's eager mode does, and each op is its own kernel that reads its inputs from global memory and writes its result back. The three temporaries (a*b, +c, relu) each make a full round trip. A fused kernel reads a, b, c once, keeps every intermediate in registers, and writes the result once. From realize() to a list of kernels

Tensor.realize() () calls linear_with_vars (), which does two things: callify the tensor graph (transform_to_call, ), then schedule it (create_linear_with_vars, ). The result is a LINEAR UOp, an ordered list of CALLs, one per kernel, which run_linear compiles and launches. Every step in between is a named graph_rewrite. The map below shows each one where it is called, with the time and graph size the capture recorded for softmax:

In order, as the harness recorded them for every example: number the uops, early transform tensor graph, finalize call, replace bufs, then multi_pm, earliest rewrites, convert copy to store, get realize, apply rangeify, add device to deviceless, symbolic+reduce_collapse+debuf, limit buffers, stage to store, one kernel split per kernel, split kernels, remove indexing from call args, schedule to linear, params to buffers, resolve linear call and create COPY kernels for SDMA. Small helper rewrites named reshape and minimum_valid also appear: rangeify calls them to simplify index expressions.

Callify: a reusable function

The first four passes rewrite the user's graph into a self-contained function. number the uops tags the nodes that must end up in memory (the realize targets; you saw its .rtag((0,)) in Chapter 2). early transform tensor graph turns each tagged node into a store into a fresh buffer: buf.after(buf.store(value)). finalize call records which Tensor will become which buffer. replace bufs replaces every concrete BUFFER with a numbered PARAM and wraps the graph in a CALL whose arguments are the real buffers. After it, the fused_chain graph reads c4.after(c4.store(c17)) with PARAM 0 as the output and PARAMs 1 to 3 as inputs.

Why the PARAMs? The schedule is cached on the function's key (lower_sink_to_linear, ). With buffers abstracted, a training step that runs the same graph on new data every iteration hits the cache, and none of the passes below runs again.

Schedule: get_kernel_graph

On a cache miss, get_kernel_graph () runs the real work. Its steps, in source order:

tsink = graph_rewrite(sink, multi_pm, name="multi_pm")                    # multi-device; no-op on one GPU
tsink = graph_rewrite(tsink, pm_mops+earliest_rewrites, bottom_up=True, name="earliest rewrites")
tsink = graph_rewrite(tsink, pm_copy_to_store, ..., name="convert copy to store")
tsink = run_rangeify(tsink, bool(DEBUG_RANGEIFY))                          # get realize, apply rangeify, ...
tsink = graph_rewrite(tsink, symbolic+pm_reduce_simplify+pm_const_buffer_folding+pm_remove_bufferize,
                      name="symbolic+reduce_collapse+debuf")
tsink = graph_rewrite(tsink, pm_limit_bufs, ..., name="limit buffers")
tsink = graph_rewrite(tsink, pm_add_buffers+pm_add_param_range_tags, ..., bottom_up=True, name="stage to store")
tsink = graph_rewrite(tsink, split_kernels, bottom_up=True, name="split kernels")
tsink = graph_rewrite(tsink, pm_no_indexing_calls, name="remove indexing from call args")

earliest rewrites folds chains of movement ops and, among other things, splits very large reductions in two (split_reduceop, ), which Chapter 5 covers. The middle three steps are where fusion is decided, and the rest of this chapter is about them. After get_kernel_graph, create_schedule () orders the kernels: it is not a rewrite but a topological sort over the AFTER edges that connect a kernel that writes a buffer to the kernels that read it.

Rangeify: from tensors to loops

The tensor graph speaks in whole tensors: "reshape this", "reduce that over axis 1". Kernels speak in loops: "for every row r0 and column r1, load x[r0*1024 + r1]". Rangeify is the translation. Every node gets a tuple of RANGE UOps, one loop variable per axis of its shape, and then the graph is rewritten so each value is an expression over those variables.

Ranges flow backwards, from consumers to producers. run_rangeify () builds a consumer map and walks the nodes in reverse toposort order, so every node is visited after all of its consumers. The comment at the heart of the walk states the rule ():

# *** the ranges on the output are
#  1. new if this op is realized
#  2. from the single consumer if this op only has one consumer
#  3. potentially new if this op has 2+ consumers

Case 2 is fusion. A node with one consumer uses the consumer's loop variables, which means it is computed inside the consumer's loop, so it needs no buffer. Case 1 starts a new loop nest: the node's value is materialized and consumers read it back. Case 3 checks whether all consumers index the node the same way. If they do, the node can still share their loops; if not, every axis gets a new range and the node is realized (with PCONTIG set, only the mismatched axes).

Movement ops don't move data; they transform index tuples. apply_movement_op () is the definition: a PERMUTE reorders the ranges, a SHRINK adds an offset, an EXPAND drops the range of a broadcast axis, a PAD adds a validity condition, and a RESHAPE flattens the ranges with strides and splits them again with // and %, which symbolic simplification then cleans up. Chapter 4 is about this arithmetic. For scheduling it is enough to know that after rangeify there are no movement ops left, only index expressions.

When a reduce forces a kernel boundary

Look at steps 4 and 6 again. x.max(-1, keepdim=True) produces one value per row, and x - max broadcasts it back across the row. To produce element [r4, r5], the consumer needs the max of row r4, and that max is itself a loop over every column. If the max were fused into the consumer's loop, every element would recompute its row's max: 1024 reads per element instead of one. The scheduler detects this pattern explicitly. While walking, it tracks ending ranges: ranges a consumer iterates that this node is broadcast over ():

ending_ranges[x] = sum([ending_ranges.get(u, []) for u in consumer_map[x]], [])
# ranges the consumers iterate that this node broadcasts over
ended = [rctx.range_map[c][0][i] for c in consumer_map[x] if c in rctx.range_map and c.op in GroupOp.Broadcastable
         for i in broadcast_axes(x.shape, c.shape)]
broadcast_ending_ranges = list(UOp.sink(*ended).ranges)
# fusion decision: REDUCE before the broadcast
if x.op is Ops.REDUCE: ending_ranges[x] += broadcast_ending_ranges

and then, if a REDUCE (or elementwise op) has non-empty ending ranges, its output axes are realized with new ranges (). That is the rule that splits softmax: the max is broadcast back over the reduced axis, so it is realized; so is the sum. Layernorm has the same shape, with mean and variance in place of max and sum. A reduce whose result is not broadcast back, like a.exp().sum(1), fuses with what feeds it into one kernel.

STAGE, then the cost model

apply rangeify (, a bottom-up rewrite with the range map as ctx) materializes these decisions. Buffers and PARAMs are read with .index(...), a REDUCE gets explicit reduce ranges, movement ops are deleted, and every realized value is wrapped in a STAGE (the comments still call it BUFFERIZE): "materialize this value over these closed ranges". For softmax that is five materialization points: the input, the max, the exp, the sum, and the output STORE.

The realize map is deliberately generous, and the next pass trims it. symbolic+reduce_collapse+debuf includes remove_bufferize (), a small cost model that decides per STAGE whether to keep it or to substitute the consumer's indices into the STAGE's source, inlining and recomputing it. A STAGE stays if the user asked for it (.contiguous()), if its source reads more than three buffers, or if any reduce inside it reads a buffer (, ). Otherwise it is removed. For softmax, the input STAGE and the exp STAGE contain no reduce, so they go: exp is recomputed in both the sum kernel and the final kernel, which is cheaper than writing and re-reading a 4 MiB intermediate. The max and sum STAGEs each wrap a reduce over the input, so they stay.

stage to store (bufferize_to_store, ) turns each surviving STAGE into a BUFFER, a STORE into it, an END that closes the loops, and an AFTER that readers go through. Finally, split kernels cuts the graph at each STORE or END with no open ranges (split_store, ): each becomes a SINK with KernelInfo, wrapped in a CALL whose arguments are its buffers. Inside, a local kernel split rewrite renumbers PARAMs and ranges from 0, so identical kernels hash the same and are compiled once.

Kernels 0 and 1 are both named r_1024_16_64: a reduction (r) with 1024 blocks of 16 threads, each thread covering 64 elements of its row (the GROUPTOP opt; Chapter 5). Kernel 2 is elementwise (E_128_16_8_16_4). Kernel 1 reads PARAM 2, the 1024 maxes written by kernel 0, and kernel 2 reads both 1024-float vectors plus x again. Each of the three passes over x reads 4 MiB, so softmax moves about 16 MiB; the per-kernel estimates.mem codegen computed (4,198,400, 4,202,496 and 8,396,800 bytes) match the shape arithmetic exactly. Layernorm has the same structure: a mean kernel, a variance kernel that stores sqrt(var + 1e-5), and an elementwise normalize.

The same caveats about timing apply. The structural difference is visible anyway: one kernel against three.

What PyTorch does differently

Eager PyTorch runs softmax as one hand-written kernel, softmax_warp_forward<float, float, float, 10, ...> (7.07 µs). For rows of up to 1024 elements it gives each row to a warp, which keeps the row in registers, computes the max and the sum with warp shuffles, and writes the result: one read of x, one write. Layernorm likewise has vectorized_layer_norm_kernel (9.09 µs).

Inductor generates a single fused kernel too, triton_per_fused__softmax_prepare_softmax_online_0 (5.86 µs). Its pre-fusion IR has three scheduler nodes, two reductions and a pointwise op, much like tinygrad's three kernels. The first two carry one reduction, 'online_softmax_reduce', which yields both the max and the sum. Inductor's scheduler then fuses all three into one FusedSchedulerNode. The per in the name means a persistent reduction: the whole reduced dimension fits in one block, so the kernel loads a row once into registers (R0_BLOCK = 1024), reduces it twice, and computes the outputs from the values it already holds.

Note what the persistent kernel does and does not avoid. It still computes exp twice (tmp8 and tmp14), just as tinygrad recomputes it. What it avoids is the broadcast boundary: the max and sum never leave the block, so they need no global buffer, and x is read once instead of three times. tinygrad's rangeify sees a reduce broadcast back over its own axis and cuts there, because in its model a value that every element of a row needs must be complete before the row is read again. Getting from three kernels to one needs the knowledge that a row fits in registers or shared memory, which is a codegen fact, not a graph fact. tinygrad's scheduler has hooks in this direction (the PCONTIG setting allows partial, LOCAL-memory stages in remove_bufferize), but at the captured commit the default is the three-kernel schedule you see here.

For elementwise chains the two compilers agree. gelu is one tinygrad kernel (E_8192_32_4) and one Inductor kernel (triton_poi_fused_gelu_0), and fused_chain is one kernel in both, against four in eager mode.

Two more limits can split kernels. limit buffers () splits a kernel that would read more buffers than the device allows; the table lists Metal, WebGPU and CPU but not CUDA, so on the L4 it never fires unless you set MAX_KERNEL_BUFFERS. And split_reduceop splits a reduction whose input is at least 32768 times larger than its output into two kernels for parallelism: the sum_all capture (a 4096×4096 sum) runs as r_32_32_4_1024_4, r_256_16 and r_16_16, which Chapter 5 explains.

Summary

  • realize() callifies the graph (buffers become PARAMs, so schedules are cached), then get_kernel_graph runs rangeify, the cost model, buffer creation and kernel splitting, and create_schedule orders the kernels by their AFTER edges.
  • Rangeify gives every node loop variables, flowing from consumers to producers. A single consumer means shared loops, which is fusion. Realized nodes get new loops and a STAGE; movement ops become index math and disappear.
  • A reduce whose result is broadcast back over the axes its consumer iterates is realized: this is why softmax and layernorm are three kernels in tinygrad.
  • remove_bufferize undoes realizations that are cheap to recompute (no reduce over a buffer, at most three buffers); surviving STAGEs become BUFFER + STORE + END + AFTER, and each closed store is a kernel.
  • Inductor fuses softmax into one persistent-reduction kernel that keeps each row on chip; eager PyTorch has a hand-written warp-per-row kernel. Both read x once. For elementwise chains, tinygrad and Inductor both produce one kernel.
