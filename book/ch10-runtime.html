Chapter 10

Runtime, TinyJit and autograd

The previous chapters followed a single realize() from the Tensor graph to SASS. This one covers what happens around it. A gradient in tinygrad is more UOp graph, built by a pattern matcher and compiled by the same scheduler and codegen. A compiled kernel is loaded into the CUDA driver and launched with a packed argument struct. TinyJit records the kernel list once and replays it, which skips Python graph building, scheduling and compiling on later calls. Each step is shown against L4 captures, with PyTorch's autograd, Inductor and CUDA graphs alongside for comparison.

Autograd is graph construction

PyTorch's eager autograd records a tape while the forward pass runs. Every op that needs a gradient stores a backward node and the tensors it will need, and .backward() walks that tape and launches backward kernels. tinygrad has nothing to record. When you write (x @ w).relu().sum(), no kernel has run yet, and the Tensor is a lazy UOp graph (Chapter 2). So the gradient is a graph transformation: walk the forward graph backwards, and for each node emit new UOps that compute the gradient of its inputs. The output is another lazy graph. Nothing runs until you realize it.

The entry point is Tensor.gradient(*targets). If no output gradient is given, it seeds one with self.const_like(1.0) and calls compute_gradient(root, root_grad, targets) . Tensor.backward() is a thin wrapper. It collects every live float tensor in the graph, calls gradient for all of them, and stores the results in .grad –. Those .grad tensors are lazy too.

compute_gradient in about forty lines

compute_gradient works in three steps:

  1. Find the path. _deepwalk toposorts the graph and keeps only the nodes that lie between the root and one of the targets. A branch that cannot reach w, such as the path to x when you only ask for dL/dw, gets no gradient. DETACH stops the walk.
  2. Apply one rule per node, root first. For each node in reverse topological order, it looks up the node's gradient so far (grads[t0]) and rewrites the node with the pattern matcher pm_gradient, passing that gradient as ctx . Each rule returns one gradient per source.
  3. Fix shapes and accumulate. If a source's shape differs from its gradient's shape (broadcasting lives in _shape, so a MUL of a (256,1,512) and a (1,256,512) is legal), the gradient is summed down to the source's shape . If the source already has a gradient (it is used twice), the two are added .

The rules themselves are ordinary UPat → lambda entries, the same machinery as every other rewrite in the book. The ones our example needs are below:

# tinygrad/mixin/gradient.py   (ctx is the gradient flowing into the node)
def reduce_gradient(ctx:UOp, ret:UOp, op:Ops):
  if op == Ops.ADD: return (ctx._broadcast_to(ret.src[0].shape),)          # line 9
  ...
pm_gradient = PatternMatcher([
  (UPat((Ops.CMPLT, Ops.CMPNE)), lambda: (None, None)),                     # line 59: comparisons have no gradient
  (UPat(Ops.ADD), lambda ctx: (ctx, ctx)),
  (UPat(Ops.MUL, name="ret"), lambda ctx, ret: (ret.src[1]*ctx, ret.src[0]*ctx)),   # line 65
  (UPat(Ops.WHERE, name="ret"), lambda ctx, ret: (None, ret.src[0].where(ctx, ctx.const_like(0)),
                                                     ret.src[0].where(ctx.const_like(0), ctx))),  # line 66
  (UPat(Ops.REDUCE, name="ret"), lambda ctx, ret: reduce_gradient(ctx, ret, ret.arg[0])),         # line 67
  (UPat(Ops.RESHAPE, name="ret"), lambda ctx, ret: (ctx.reshape(ret.src[0].shape), None)),         # line 70
  (UPat(Ops.EXPAND), lambda ctx: (ctx, None)),
  (UPat(Ops.PERMUTE, name="ret"), lambda ctx, ret: (ctx.permute(argsort(ret.marg)),)),             # line 74
  ...
])

There is no "matmul backward" or "relu backward" rule, because neither op exists by the time the gradient runs. dot builds the matmul from reshapes, a transpose, a broadcasting MUL and a sum –. _rop permutes the reduced axes to the front before emitting REDUCE , which is why a PERMUTE sits under every reduce. relu is (self > 0).where(self, 0) . The comment above it explains the choice: written as maximum(0), the MAX rule would pass half the gradient through at exactly zero. So the gradient of a matmul falls out of the MUL, REDUCE and movement rules, and the gradient of relu falls out of the WHERE rule.

The gradient goes through the same compiler

After compute_gradient returns, nothing about the graph says "backward". The harness realizes loss.gradient(w)[0], and the scheduler and codegen see a graph of MUL, REDUCE, WHERE and movement ops like any other. Step through the passes. The tensor-stage IR is the gradient graph. apply rangeify creates two STAGEs. symbolic+reduce_collapse+debuf removes the one on x and keeps the one on the mask. split kernels cuts the graph into two kernels.

Why two kernels, and which two

The fusion rules from Chapter 3 decide this. The mask (0 < Σ x·w).where(1, 0) ends in a REDUCE, and its consumer broadcasts it over a new axis: the 512-long EXPAND in the second matmul. That is the "reduce before the broadcast" decision in rangeify , the rule that splits softmax. The cost model remove_bufferize could still inline the STAGE, but it refuses when a REDUCE inside the source reads a buffer –. Recomputing a 512-long dot product for every element of the next matmul would be far too expensive. So the mask gets its own buffer and its own kernel.

Kernel 0 is r_8_4_8_16_4_4_128_4. Its AST stores (0 < Σk x[i,k]·w[k,j]).where(1.0, 0.0) into a 65536-float buffer. Look at the source: the whole forward matmul runs in this kernel, 16 accumulators per thread over 128 iterations of an unrolled-by-4 loop. The product x@w stays in registers and is never written to memory. Only the comparison result reaches memory, as 0.0 or 1.0:

Kernel 1 is r_8_8_8_16_4_4_64_4, the second matmul. Its AST is out[j*512+k] = Σi x[i*512+k] · mask[i*256+j], a 256-long reduction (64 iterations × 4 unrolled). The indexing shows a detail you would miss from the Python. The output buffer is laid out as (256, 512), so it holds mask.T @ x. The gradient tensor, shape (512, 256), is a PERMUTE view of that buffer: the last lines of the tensor graph end in PERMUTE(..., (0, 2, 1)) followed by a RESHAPE. Realizing the gradient only had to produce some buffer it can be viewed from. A CPU experiment confirms the cost of this: g.realize() runs 2 kernels and a following g.numpy() runs a third, an E_ copy that makes the view contiguous. The L4 capture only times the two realize kernels.

Both kernels got the same opts (UPCAST 4, UPCAST 4, UNROLL 4, LOCAL 8, LOCAL 16) and the same 56 registers. They do almost the same number of FLOPs (the ops estimates are 67,239,936 and 67,108,864). Yet kernel 0 took 70.66 µs and kernel 1 took 37.89 µs. The difference is probably memory access. A warp here is 8 threadIdx.x lanes × 4 threadIdx.y rows. In kernel 0, the x load address is (gidx1<<14)+(lidx0<<11)+(Ridx0<<2), so the 8 threadIdx.x lanes read float4s 2048 floats apart. In kernel 1, the threadIdx.x term of the mask load is lidx0<<2, so those lanes read 8 consecutive float4s, and the other operand (indexed by lidx1) is shared across them. That is an inference from the source, not a profiler measurement.

Recompute instead of store? In this capture nothing was "stored by the forward pass" at all, because there was no separate forward pass. We asked for dL/dw only, so the loss and the relu output were never computed (the faded nodes in the last animation step). The forward matmul exists only inside kernel 0. What happens if you also want the loss? A second CPU experiment, Tensor.realize(loss, g), schedules 4 kernels: one stores x@w itself (65536 floats), a two-stage reduction computes relu and sum from that buffer, and the gradient matmul recomputes the mask 0 < s ? 1 : 0 from the same buffer on the fly. The scheduler sees the forward and backward graphs together and shares the matmul between them. No kernel stores the relu output or the mask, as a PyTorch saved tensor would.

PyTorch: a tape, saved tensors, cuBLAS

The torch capture computes the same gradient with (x @ w).relu().sum().backward(). In eager mode that is a forward pass followed by a backward pass, 7 kernels in total. Open the Eager kernels tab:

  • forward x @ w: a CUTLASS SIMT SGEMM (cutlass_80_simt_sgemm_128x64_8x5_nn_align1, 8.93 µs) plus cuBLASLt's splitKreduce_kernel (3.39 µs). cuBLAS split the K=512 reduction across blocks and added the partial results in a second kernel.
  • forward relu: launch_clamp_scalar (1.47 µs). The relu output is materialized because autograd saves it for the backward.
  • forward sum: reduce_kernel<512, 1, ...sum_functor...> (8.0 µs).
  • backward seed: FillFunctor (1.06 µs) writes the 1.0 that .backward() starts from.
  • relu backward: threshold_kernel_impl (1.89 µs). It reads the saved relu output and writes the masked gradient.
  • x.T @ grad: ampere_sgemm_32x32_sliced1x4_nt (10.94 µs).

Under torch.compile, AOTAutograd traces forward and backward into one joint graph and partitions it. The FX graph tab shows the compiled backward graph and its inputs. It takes le: "b8[256, 256]", a bool mask saved by the forward, plus permute: "f32[512, 256]" (x.T, a view with strides (1, 512)) and tangents_1, the incoming scalar gradient. The partitioner chose to save one byte per element instead of the float relu output, and the forward kernel triton_red_fused_relu_sum_threshold_backward_0 writes that mask while it computes partial relu-sums; a second forward kernel, triton_per_fused_relu_sum_1 (1.15 µs), adds the partials into the loss. The backward is one Triton pointwise kernel, triton_poi_fused_expand_threshold_backward_0 (where(le, 0, tangent)), and then extern_kernels.mm, which is cuBLAS again. Both matmuls stay in vendor libraries.

The totals are 108.55 µs for tinygrad, 35.68 µs for eager and 27.78 µs for Inductor. PyTorch does more work, since it also computes the loss, and still finishes 3–4× sooner. Nearly all of the gap is the two matmuls: cuBLAS/CUTLASS take about 23 µs (with split-K) where tinygrad's hand-coded-opts kernels take 108 µs. The structural difference is the interesting part of this chapter, though. PyTorch's autograd is a runtime mechanism that saves tensors from a forward pass that has already run. tinygrad's is a compile-time graph construction, and the scheduler alone decides what to store and what to recompute.

From PROGRAM to cuLaunchKernel

Everything so far produced a LINEAR: a list of CALLs, each holding a compiled PROGRAM (source + binary + ProgramInfo) and the buffers it touches. run_linear executes it. When not in the JIT, it first calls compile_linear (codegen for every kernel that is not in to_program_cache, in parallel worker processes). It then walks the calls and dispatches each one through the pm_exec pattern matcher , which routes it to exec_kernel, exec_copy or exec_graph. For a kernel:

# tinygrad/engine/realize.py:180-190  exec_kernel (excerpt, inside the per-device loop)
prg_bufs = [b.ensure_allocated() for b in bufs]          # allocate on first use
rt = get_runtime(device, ast, cache=ctx.cache)            # CUDAProgram, cached by (ast.key, device)
global_size, local_size = ast.arg.launch_dims(var_vals)   # symbolic sizes resolved here
ets.append(rt(*[b.get_buf(device) for b in prg_bufs], global_size=global_size, local_size=local_size,
              vals=ast.arg.vals(var_vals), wait=ctx.wait, timeout=ctx.timeout))

Loading: cuModuleLoadData

get_runtime builds Device["CUDA"].runtime(ast.to_elf()) once per kernel and device and caches it in runtime_cache. For CUDA the runtime is CUDAProgram. Its constructor sets the context, calls cuModuleLoadData on the compiled bytes , and looks the kernel up by name with cuModuleGetFunction . On the CUDA device NVRTC was asked for PTX, not a cubin (ptx=... or dev == "CUDA", ). The PTX-to-SASS step therefore happens inside the driver, during this cuModuleLoadData call. The SASS shown throughout this book was produced separately with ptxas -arch=sm_89, as the kernel-view notes say.

Launching: one struct, one call

The first call packs the arguments into a ctypes struct with encode_args . Buffer pointers become 8-byte CUdeviceptr fields f0, f1, … at offsets 0, 8, 16, …. Integer kernel arguments (symbolic Variables, see below) follow as v0, v1, … at the offsets the kernel signature gives. The struct is passed through the extra array (CU_LAUNCH_PARAM_BUFFER_POINTER, the struct pointer, CU_LAUNCH_PARAM_BUFFER_SIZE, its size, CU_LAUNCH_PARAM_END), not kernelParams. Later calls skip encode_args and just overwrite the fields . Then:

# tinygrad/runtime/ops_cuda.py:65
return cu_time_execution(lambda: check(cuda.cuLaunchKernel(self.prg, *global_size, *local_size, self.smem, None, None, self.vargs)),
                         enable=wait)

tinygrad's global_size is the CUDA grid in blocks and local_size is the block in threads. For kernel 0 above (grid 4 × 8 × 1, block 8 × 16 × 1) the call is cuLaunchKernel(prg, 4, 8, 1, 8, 16, 1, 0, NULL, NULL, extra). That is 32 blocks of 128 threads, matching __launch_bounds__(128) in the source. The stream argument is None, the default stream, so launches run in order. With wait=True, cu_time_execution records a CUDA event before and after the launch, synchronizes on the second, and returns cuEventElapsedTime –. DEBUG>=2 forces wait , which is where every L4 time in this book comes from. It also means that at DEBUG=2 every launch is synchronous.

Memory: the allocator and the arena

Buffers are allocated lazily (ensure_allocated) through the device's allocator. CUDAAllocator calls cuMemAlloc_v2. Host-to-device copies are staged through pinned memory from cuMemHostAlloc and sent with cuMemcpyHtoDAsync_v2; the staging buffers are freed at the next synchronize. Device-to-host copies synchronize first. The allocator is an LRUAllocator . A freed buffer goes into a cache keyed by (size, options), and the next allocation of the same size takes it back without touching the driver. Only when cuMemAlloc fails is the cache emptied and the allocation retried.

Before any of that, the schedule's intermediate buffers are planned. memory_plan_rewrite runs at the end of every schedule and again at JIT capture. It records the first and last kernel that touches each internal buffer, then replays those open/close events through a TLSF suballocator, rounding every buffer to 256 bytes. Buffers whose lifetimes do not overlap share bytes. The result is one int8 arena per device (copy buffers get a separate lane), and every buffer becomes arena[off:off+n].bitcast(dtype) . In mlp_backward the 256×256 mask is such an intermediate: kernel 0 writes it, kernel 1 reads it, and nothing else holds it. Buffers that a live Tensor can still see (held_bufs) are never planned.

The NV backend: the same launch without libcuda

DEV=NV is a second NVIDIA backend that does not use the CUDA driver API. All captures in this book were made with DEV=CUDA, so this section is a source reading and has no L4 numbers. NVDevice picks an interface. The default NVKIface opens /dev/nvidiactl, /dev/nvidia-uvm and /dev/nvidiaN and talks to the kernel driver's resource manager with raw ioctls (rm_alloc, rm_control ). PCIIface goes further and drives the GPU over PCI with no kernel driver at all. tinygrad allocates its own channel, GPFIFO rings and command buffers in memory mapped into Python.

A launch is then just writing memory:

  • NVComputeQueue.exec copies the program's prebuilt QMD (Queue Meta Data, the hardware's launch descriptor) next to the argument buffer. It writes the grid size and the block size into the QMD fields – and points constant buffer 0 at the arguments .
  • Submission writes a GPFIFO ring entry that points at the command buffer, bumps GPPut, issues a memory barrier and rings the doorbell register gpu_mmio[0x90//4] .
  • No driver loads the code here, so the program must be a real ELF cubin, which tinygrad's own elf_loader relocates . That is why the CUDA renderer asks NVRTC for a cubin on NV and PTX on CUDA.

Its graph type is the generic HCQ graph, which builds the command queue once and patches it, instead of a CUgraph.

TinyJit: capture once, replay forever

Even with every cache warm, each un-jitted call still pays for Python building the Tensor graph, the schedule cache lookup (which hashes the graph), compile_linear resolving programs, and Python walking the calls one by one. For a training step with hundreds of kernels that overhead dominates. TinyJit removes almost all of it. The capture below wraps one function and calls it four times with new inputs:

# harness/jit_demo.py (run on the L4 with DEV=CUDA, DEBUG=2 per call)
w = Tensor(np.random.default_rng(0).standard_normal((512, 512), dtype=np.float32)).realize()

@TinyJit
def step(x: Tensor) -> Tensor:
  return ((x @ w).relu() * 2 + 1).sum(1).realize()

for i in range(4):
  x = Tensor(np.full((256, 512), i + 1, dtype=np.float32)).realize()
  y = step(x)

The three states of cnt

_TinyJit.__call__ branches on a counter. The captured jit_cnt_after values above, 1, 2, 3, 4, are that counter after each call .

  • cnt == 0: run normally . The function runs as plain tinygrad: build the graph, schedule, compile, run. This warms every cache, and it is how BEAM search (if enabled) gets to pick opts before anything is frozen. Call 0's kernel line has a green header in a terminal because it is the first run of that kernel (first_run_cache, ). The capture stores logs without color codes.
  • cnt == 1: capture . The JIT puts itself in the global capturing list and runs the function again. Python rebuilds the graph and the scheduler builds the LINEAR. But at the end of create_linear_with_vars the scheduler sees capturing, hands the linear to the JIT with add_linear, and returns an empty LINEAR –, so nothing runs yet. Then it prints JIT captured 1 linears with 1 inputs (one realize, one Tensor argument; w is not an input, its buffer is baked into the captured calls). It concatenates the linears and runs jit_lower , which does four things:
    1. replaces each input buffer with a PARAM slot
    2. memory-plans the intermediates
    3. compiles everything (with JITBEAM if set; here every kernel is already in to_program_cache)
    4. groups kernels into graph batches
    Finally it wraps the result in a CapturedJit and executes it . That is why call 1 still shows its kernel line, now printed with ctx.jit=True (a magenta header).
  • cnt ≥ 2: replay . The Python function is not called. _prepare_jit_inputs extracts the input buffers and any bound Variables. Their names and (view, variables, dtype, device) must match the capture or you get JitError("args mismatch in JIT"). Then CapturedJit.__call__ runs run_linear(self.linear, var_vals, input_uops=..., jit=True) , and jit=True skips compile_linear entirely . Calls 2 and 3 print only their kernel lines.

Swapping inputs

Each replay must read the new x. During capture, jit_lower substituted every input buffer with UOp.param(i, ...) . At replay, resolve_params maps each PARAM slot to input_uops[slot], the buffers of this call's arguments –. CUDAProgram then writes the new pointer into the f field of its argument struct. The captured outputs show it worked. With x filled with c = 1, 2, 3, 4 and relu being positively homogeneous, each row sum is 2·c·S + 512, so y[0] should be linear in c. It is: 9831.30, 19150.61, 28469.90, 37789.21, in steps of 9319.30. Two details follow from the code. If the captured kernels write into an input, the JIT copies that input first (_copy_input, ). And the return value is the same Tensor object every replay (return self.ret, ), with its buffer overwritten, which is why the harness reads y[0] right after each call.

The kernel it replays

The whole function, matmul + relu + *2 + +1 + row sum, fused into one kernel, r_256_16_512_32. The capture records its name and timings but not its source, so below is the CUDA C that tinygrad renders for this graph. It was produced offline (CPU experiment) with NVCCRenderer for sm_89 from the same commit. That renderer prints the same C as CUDARenderer and only swaps NVRTC for nvcc, and the kernel name and launch dims match the L4 capture. There are 256 blocks of 16 threads. Each thread computes 32 output columns of x@w one 512-long dot product at a time, applies relu·2+1, and accumulates. A shared-memory step then sums the 16 partial row sums. It is correct but slow (about 167 GFLOPS). In this offline render the heuristic applied a single opt, GROUPTOP over the 512 output columns, and none of the upcasts that gave kernel 0 above its 16 accumulators per thread.

Batching into CUDA graphs

With one kernel there is nothing to batch, so the capture contains no CUDA graph. The last step of jit_lower is graph_split_rewrite . It walks the captured calls and collects consecutive ones that the device's graph class supports (CUDAGraph is a MultiGraphRunner: PROGRAMs and COPYs on devices of one type, ). A batch of one is left alone unless GRAPH_ONE_KERNEL=1 . That is the case here: calls 2 and 3 are each one plain cuLaunchKernel. Larger batches become a CUSTOM_FUNCTION(arg="graph") call, and DEBUG=2 prints JIT GRAPHing batch with N kernels. Batch sizes start at JIT_BATCH_SIZE = 32 and double after each flushed batch (max_batch_size *= 2, ), so a long step becomes graphs of 32, 64, 128, … kernels. The first batch starts executing early, and the number of graph launches stays small.

At first execution exec_graph builds a CUDAGraph . It calls cuGraphCreate, then one cuGraphAddKernelNode per kernel with the same grid, block and packed-args extra as a direct launch. Each node's dependencies come from a read/write tracker over the buffers, so independent kernels may overlap. It finishes with cuGraphInstantiate. Each replay then patches only what changed: input pointers, Variable values and symbolic launch dims, through cuGraphExecKernelNodeSetParams –. It then issues one cuGraphLaunch , and DEBUG=2 shows that launch as a single line named batched N . Use the second mode of the timeline above to see the difference. JIT=2 keeps the JIT but disables graphs, and JIT=0 disables the JIT.

Symbolic shapes: one kernel for every n

A JIT replays fixed kernels, so a changing shape would normally mean a new capture. LLM decoding, where the KV length grows by one token per step, would recompile every step. tinygrad's answer is a Variable: a symbolic integer with bounds, bound to a value for one call. The harness runs (big[:n] * 2).sum() with n = Variable("n", 1, 1024).bind(10), then .bind(700), at DEBUG=4 on the L4:

Read the first log from the top. The schedule was a CACHE MISS, then DEBUG=4 printed the source just before compiling it (). The kernel is named r_n. The slice length is not a constant in it: n became the kernel parameter const int data2_, and the loop runs Ridx0 < data2_. The second run, with n = 700, printed cache hit 189b9319 (the same schedule key) and no source, because to_program_cache already held the program. Both sums match numpy (90 and 489300).

The value travels as an ordinary argument. ProgramInfo.vals(var_vals) turns the bound values into a tuple in the order of the program's vars . exec_kernel passes them as vals=, and encode_args places them after the pointers as c_int32 fields. For r_n the struct is f0 (output pointer, offset 0), f1 (big, offset 8) and v0 (n, offset 16). Launch dims may be symbolic too, and launch_dims(var_vals) evaluates them per call . Inside a JIT, _prepare_jit_inputs unbinds the Variables from the arguments . A CUDA graph replay writes the new values into each node's v fields and grid dims (–) before relaunching.

A symbolic size has a cost. With the reduce length unknown, the optimizer applied no upcast, local or group opts: __launch_bounds__(1), a single thread walking the whole slice. The two runs took 28.67 µs (n=10) and 31.81 µs (n=700), almost all of it fixed launch and loop overhead at this size. In real models the symbolic axis is usually one of several axes, and the kernel still parallelizes over the others.

PyTorch: CUDA graphs and dynamic shapes

Background, not from the captures. The book's torch captures use default torch.compile, which does not use CUDA graphs. Nothing below was measured here.

  • mode="reduce-overhead" enables CUDA graphs in Inductor ("CUDA graph trees"). After warm-up runs, the compiled region's kernel launches are recorded into a torch.cuda.CUDAGraph and later calls replay it. A recorded graph bakes in device addresses, so PyTorch keeps static input and output buffers. Inputs that are not already static (parameters and buffers are) are copied into the recorded placeholders before each replay, and outputs live in graph-owned memory that a later replay may overwrite. That is the same trade-off as TinyJit's self.ret. tinygrad avoids the input copy by patching pointers into the instantiated graph.
  • Dynamic shapes. Dynamo guards on input shapes. When a shape changes, the default "automatic dynamic" behavior recompiles once with that dimension symbolic (s0; Triton kernels then take sizes such as ks0 as arguments, much like data2_ above). torch._dynamo.mark_dynamic or dynamic=True asks for this up front. With CUDA graphs on top, each distinct concrete shape still needs its own recorded graph.
  • Autograd. PyTorch builds the backward from the forward tape at runtime in eager mode, and from a traced joint graph under torch.compile, where a min-cut partitioner chooses what to save. That is the le bool mask seen above. tinygrad has neither a tape nor a partitioner. The gradient is part of the graph being scheduled, and rangeify's realize rules make the save-or-recompute choice.

Summary

  • Tensor.gradient walks the lazy UOp graph and applies one pm_gradient rule per node. Matmul and relu have no rules of their own: MUL, REDUCE, WHERE and the movement rules compose into their gradients.
  • The gradient graph is scheduled like any other. For d/dw (x@w).relu().sum() the scheduler realized the relu mask, because a reduce is broadcast into the next matmul. The forward matmul therefore runs inside the mask kernel and never touches memory, and the loss itself is never computed.
  • A kernel runs as cuModuleLoadData (the driver JITs the PTX) followed by cuLaunchKernel with grid = global_size, block = local_size and a packed argument struct. Intermediates live in a planned arena, and three caches avoid repeating scheduling, codegen and NVRTC.
  • TinyJit's cnt runs, captures, then replays. A replay is input checks plus run_linear(jit=True), or one cuGraphLaunch per batch when there are several kernels. Variables turn shapes into kernel arguments, so one compiled kernel serves every size.
