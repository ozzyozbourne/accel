Chapter 7

Tensor cores

An fp16 matmul of two 2048×2048 matrices with fp32 accumulation runs in 2.84 ms on the L4's ordinary CUDA cores and in 527 µs once tinygrad uses its tensor cores. In this chapter we follow the one opt that makes the difference, TC. We see where tinygrad describes the hardware (tc.py), how the opt reshapes the loop nest so that 32 threads each hold the right pieces of a 16×16 and a 16×8 matrix, how that becomes a WMMA UOp, a __device__ helper with inline PTX, mma.sync in PTX and HMMA.16816.F32 in SASS, and why the data still reaches the registers the slow way. PyTorch's cuBLAS kernel is the yardstick.

The experiment

The matmul_fp16 example multiplies two fp16 matrices and asks for an fp32 result:

tg=lambda T: T["a"].matmul(T["b"], dtype=dtypes.float)    # a, b: 2048×2048 float16
torch=lambda X: (X["a"] @ X["b"]).float()
variants={"default": {}, "no_tc": {"TC": "0"}}

matmul(..., dtype=float) ends up in dot, which computes (x*w).sum(-1, dtype=dtype) (). In the kernel AST the product is still fp16 and is cast to float before the REDUCE: (a.index(...)*b.index(...)).cast(dtypes.float).reduce(..., arg=(Ops.ADD, 0)). You can see it in the AST tab further down. That cast is the hook the tensor-core opt looks for.

What one mma.sync does

A tensor core instruction is a small matrix multiply-accumulate performed by a whole warp. The instruction tinygrad uses on the L4 (sm_89, Ada) is

mma.sync.aligned.m16n8k16.row.col.f32.f16.f16.f32  {d0,d1,d2,d3}, {a0,a1,a2,a3}, {b0,b1}, {c0,c1,c2,c3};

It computes D = A·B + C, with A 16×16 (M×K) in fp16, B 16×8 (K×N) in fp16, and C, D 16×8 in fp32. .row.col says A is row-major and B column-major (i.e. BT is row-major), which only matters for how elements are packed into registers. .sync.aligned means all 32 lanes of the warp must execute the same instruction together. No lane holds a whole row or column. The 256 elements of A, 128 of B and 128 of C are spread over the warp's registers in a fixed pattern that the PTX ISA documents as the "fragment layout": each lane holds 8 halves of A (in four 32-bit registers), 4 halves of B (two registers) and 4 floats of C (four registers).

The pattern uses two numbers per lane: groupID = lane >> 2 (0–7) and threadID_in_group = lane % 4 (0–3). Lane L holds A rows groupID and groupID+8, at columns 2·tig, 2·tig+1 and those +8. It holds B column groupID, at k = 2·tig, 2·tig+1 and those +8. It holds C row groupID and groupID+8, at columns 2·tig and 2·tig+1. Press play to watch the lanes load their fragments in order and the mma produce C. Hover any cell, or use the slider, to pick a lane.

Two things to notice. First, each output element is a 16-long dot product, and the inputs for it are held by up to 8 different lanes (the dashed outline): the hardware exchanges operands between lanes inside the instruction. That is what makes it a warp instruction and not 32 independent ones. Second, the lanes' C elements are pairs of adjacent columns, so a lane can store c0,c1 with one 8-byte store. tinygrad's epilogue does exactly that, as we will see.

One m16n8k16 is 16·8·16 = 2048 multiply-adds, 4096 FLOPs, in a single warp instruction. An FFMA does 32 multiply-adds per warp instruction, one per lane. That ratio, and the dedicated hardware behind it, is the whole point of tensor cores.

tinygrad's description of the hardware: tc.py

tinygrad does not hard-code the fragment layout into the CUDA renderer. It describes each tensor core as a TensorCore dataclass (–), and the optimizer turns that description into ordinary axis splits. The NVIDIA entries are at –:

cuda_tc_opts = ("u0","l0","l0","l1","l1","l1","u1")  # shared by all shapes with M=16 N=8
cuda_81616 = [TensorCore(dims=(8,16,16), threads=32, elements_per_thread=(8,4,4), dtype_in=di, dtype_out=do, opts=cuda_tc_opts,
  swizzle=((('r1', 'r2', 'l2', 'l3', 'l4'), ('u1', 'r3'), ('l0', 'l1', 'u0', 'r0')),
           (('r1', 'r2', 'u0', 'l0', 'l1'), ('r0', 'r3'), ('l2', 'l3', 'l4', 'u1'))))
  for di,do in [(dtypes.half,dtypes.float), (dtypes.bfloat16,dtypes.float), (dtypes.half,dtypes.half)]]
...
cuda_sm80 = cuda_81616 + cuda_8168_f16 + cuda_8168_tf32
cuda_sm89 = cuda_sm80 + cuda_81632_f8

CUDARenderer.__init__ sets self.tensor_cores = tc.get_cuda(arch) (). For sm_89 that is eight tensor cores, tried in list order: m16n8k16 for half→float, bf16→float and half→half, m16n8k8 for half→float and half→half, m16n8k8 TF32, and m16n8k32 for the two fp8 types. The fields:

  • dims=(8,16,16) is (N, M, K) (comment at ), so WMMA_8_16_16_half_float is PTX's m16n8k16.
  • threads=32: one warp.
  • elements_per_thread=(8,4,4): A, B and C elements per lane, exactly the 8 / 4 / 4 of the fragment layout.
  • opts: how to build the 8×16 output tile out of size-2 splits. "u0" upcasts dim 0 (N) by 2. "l0" splits N by 2 into a lane bit. "l1" and "u1" do the same for dim 1 (M).
  • swizzle: how lane, upcast and reduce bits are permuted for the A and B operands so their loads match the layout. Explained below.

The opts string is the C fragment layout. Each split takes the current lowest bit of an index, so applying the seven opts in order assigns index bits:

optdimbecomeswhich bit of the 8×16 tile
u0Nupcast (register) bitn bit 0 → selects c0 vs c1
l0, l0Nlane bits 0, 1n bits 1, 2 → n = 2·(lane%4) + …
l1 ×3Mlane bits 2, 3, 4m bits 0–2 → m = lane>>2 + …
u1Mupcast bitm bit 3 → +8 rows, selects c0/c1 vs c2/c3

So C[m][n] lives in lane 4·(m%8) + n/2 and register c[(m/8)·2 + n%2], which is the PTX layout from the widget. __post_init__ checks the consistency: 2#locals = threads = 32, 2#upcasts = C elements per thread = 4, N·M = 27 ().

A and B don't use all of those bits (A doesn't depend on n, B doesn't depend on m), and they need the K bits too. K = 16 is split into four size-2 reduce bits r0..r3 (get_reduce_axes, ). The swizzle lists, for each operand, which bit to put in each lane slot, upcast slot and reduce slot. For A: lane slots (r1, r2, l2, l3, l4) mean lane bits 0–1 carry k bits 1–2 (k = 2·tig + …) and lane bits 2–4 keep the m bits (row = groupID). Upcast slots (u1, r3) are the +8 row bit and the +8 k bit. Reduce slots (l0, l1, u0, r0) hold the n bits (on which A does not depend) and k bit 0, the two halves packed in one register. That gives A's 23 = 8 elements per lane. B's swizzle does the same with the n bits on lane bits 2–4 (column = groupID) and (r0, r3) as its 2 upcast bits. The assertions at – check that these counts give 8 and 4 elements per thread.

When the TC opt applies

The heuristic tries tensor cores before anything else (–). It does so if TC (the USE_TC ContextVar, default 1, ) is positive and the kernel has exactly one reduce axis. It tries Opt(OptOps.TC, axis, (TC_SELECT, TC_OPT, TC)) for axis 0, 1 and 2, and the first that does not raise wins. Scheduler._apply_tc_opt (–) decides:

  1. The first REDUCE must be an ADD whose source is a MUL, possibly under a CAST (). Our (a*b).cast(float) qualifies.
  2. It walks the renderer's tensor cores, or only number TC_SELECT if that is not −1. On CUDA, fp32-input (TF32) cores are skipped unless ALLOW_TF32=1 (). The rest must match exactly: dtype_in equals both MUL inputs and dtype_out equals the reduce's dtype (). half·half reduced into float matches the first entry, m16n8k16 half→float.
  3. It picks the N, M and K ranges: ranges only in the second input, ranges only in the first, and reduce ranges, with axis indexing their product (–). Each must be divisible by the TC dims. Otherwise padding is needed, which requires TC_OPT ≥ 2 (). TC_OPT defaults to 0 for the heuristic, but BEAM's TC actions use 2 ().
  4. It creates one WARP range of 32 (id −1) and applies the seven opts. Each l split uses warp % 2 as its new "range" and halves the warp (–). Then it splits K four times by 2 into UNROLL ().
  5. Unless TC=2 (shape only, for debugging, ), it applies the swizzle permutation to the two MUL sources and replaces the REDUCE with UOp.wmma(a, b, zeros, dims, device, threads, tc_upcast_axes) (). The rest of the K range (2048/16 = 128) stays as a REDUCE around the WMMA ().

Back in the heuristic, a successful TC is followed by up to three more opts and then an early return. It upcasts M, then N, by the first of 5, 4, 3, 2 that divides, and adds a LOCAL of 4 (or 2) on N. Here that gives UPCAST(0,4), UPCAST(1,4) and LOCAL(1,4), the captured applied_opts:

Read the name with chapter 6's rules: 32·16 blocks; a 32-lane warp and 4 warps per block; upcasts 2·2 from the TC (the c-register bits) and 4·4 from the heuristic; a reduce loop of 128 and an unroll of 2. Of the four K bits the TC opt created, only the last (range id 8) still shows as an axis. The WMMA's A operand is built over it, which is visible in the tc_upcast_axes of the IR below. It is not an extra factor of K: 128 iterations × 16 = 2048. With TC=2, which applies the shape without building a WMMA, a variant of the CPU experiment (tc2.py) prints r_32_16_32_4_2_2_4_4_128_2_2_2_2, with all four bits.

What one warp computes per loop iteration: the 4×4 upcast makes it 4 A fragments (64 rows) × 4 B fragments (32 columns), i.e. 16 mma per iteration. A block is 4 warps side by side along N: 64×128 outputs. The grid of 32×16 blocks covers 2048×2048. TC=0 removes the TC attempt. The heuristic then takes the same path as the fp32 matmul in chapter 6 and produces r_64_32_8_16_4_4_512_4.

The WMMA UOp through the passes

The TC opt is applied inside apply_opts, which is not a named pass. The first snapshot that contains the Ops.WMMA is flatten range. Its arg is ((8, 16, 16), dtypes.half, 'CUDA', 32, tc_upcast_axes), the warp is UOp.range(32, -1, AxisType.WARP), and the lane bits appear as chains of //2 and %2 on it. Step forward:

  • expander: expand_wmma () contracts the upcast axes into the WMMA's operand vectors. The arg's last field becomes None, and the operands become RESHAPE/PERMUTE of vectorized loads.
  • remove reduces: the accumulator becomes float buf0[64] (16 tiles × 4 floats), and pm_wmma_add () folds the accumulate into the WMMA's C operand.
  • *** expand broadcast / add loads and devectorize2: broadcast_and_devec_wmma () splits the 4×4 grid of tiles into 16 separate WMMAs, and loads are devectorized into scalars. The graph grows from 106 to 1021 UOps.
  • Memory coalescing (which runs just before add images and is not a named pass in the capture) regroups adjacent scalar loads into vector loads; the node count drops to 947. A's pairs (adjacent along k) become half2. B's pairs are 2048 elements apart along k, so they stay scalar.

Rendering: a __device__ helper with inline PTX

CUDA C has no portable operator for this instruction, so the renderer emits one helper per distinct WMMA (CUDARenderer.render_kernel, –). It maps dtypes to PTX type names (half → f16, float → f32, ). It counts 32-bit registers per operand as elements·itemsize/4: 8 halves → 4, 4 halves → 2, 4 floats → 4. Then it writes an asm statement that ties C to the output with "+r" (read-write). The WMMA UOp itself renders as a call, __WMMA_8_16_16_half_float(a, b, c) ().

In the source, the lane index is lidx0 = threadIdx.x (32), and the fragment layout appears as alu1 = (lidx0>>2) (groupID) and alu4 = (lidx0&3) (threadID_in_group). For A, alu3 adds alu1<<11 (row groupID; a row is 2048 halves) and alu5 = alu4<<1 adds column 2·tig. For B, alu70 adds alu1 (column groupID) and alu4<<12 (k = 2·tig, two rows of 2048). Each make_half8 then packs four half2 loads into an A operand, and each make_half4 packs four scalar halves into a B operand. We can check these against the PTX layout mechanically. PTX and SASS: mma.sync becomes HMMA.16816.F32

NVRTC compiles the inline asm verbatim: on the PTX tab above there are 16 mma.sync.aligned.m16n8k16.row.col.f32.f16.f16.f32 lines per loop iteration. Notice how the same A registers ({%r220, %r221, %r222, %r223}) are reused across four of them, and the same B registers across another four: that is the 4×4 upcast doing register reuse at the fragment level. ptxas turns each into one SASS instruction, HMMA.16816.F32 (on the SASS tab, e.g. HMMA.16816.F32 R32, R72.reuse, R76, R32). The .reuse flag tells the hardware to keep the A operand in the operand-reuse cache for the next instruction. The loop runs 128 times (ISETP.NE.AND P0, PT, R84, 0x80).

The default kernel has 16 HMMA, 32 LDG and 32 STG. 32 CS2R zero the 64 accumulator registers two at a time, which accounts for most of the 92 registers ptxas reports (64 accumulators + 8 A + 8 B operand registers (ptxas keeps two A fragments live and reloads them) + addresses).

Synchronous, and no ldmatrix

mma.sync is synchronous. It is an ordinary instruction in the warp's stream. It reads its operands from registers and writes its result to registers, and the scheduler stalls a dependent instruction until the result is ready, exactly as for an FFMA with a longer latency. Nothing is asynchronous here. The asynchronous form, wgmma.mma_async, which is issued by a 128-thread warpgroup, reads B from shared memory (A may come from registers or shared memory) and is waited on with wgmma.wait_group, exists only on Hopper (sm_90a). It is not available on the L4's sm_89.

The data path is global memory → registers. The SASS has no LDS, no LDSM and no BAR: tinygrad's hand-coded TC kernel uses no shared memory at all. ldmatrix (SASS LDSM) loads 8×8 tiles from shared memory directly into the fragment layout, so it cannot help a kernel that never stages data in shared memory. Instead, every lane fetches its own fragment elements from global memory (through L1/L2):

  • A: 16 LDG.E (32-bit) per iteration, each a half2, since A's fragment pairs are adjacent along k, which is the contiguous direction of row-major A.
  • B: 16 LDG.E.U16 (one half each), then 8 PRMT (byte permute) instructions to pack pairs into the 32-bit b registers. B's pairs run along k, which for row-major B means 4096 bytes apart.
  • C: 32 STG.E.64 in the epilogue, one per (c0,c1) or (c2,c3) pair.

Within a warp, lanes with the same groupID read neighbouring bytes, and the caches absorb a lot of the reuse. But each fragment is reloaded by every warp that needs it, with 2-byte loads for B. This is the main reason tinygrad's TC kernel reaches about 27% of the tensor-core peak while cuBLAS reaches about two thirds.

Without tensor cores: TC=0

With TC=0 the same AST goes through the fp32 recipe from chapter 6: 4×4 register tile, unroll 4, 8×16 threads. The source keeps the AST's numerics literally: each product is computed in half and then cast:

ptxas maps this to HMUL2 (two fp16 products in one instruction), two HADD2.F32 (adding −0 to a half, which converts it to fp32) and two FADD. That is five instructions for two multiply-adds, where an fp32 kernel would use two FFMAs. The products are also rounded to fp16 before they are accumulated, which is why this variant's error is 0.0475 against the tensor-core kernel's 0.00125: the tensor core does not round each product to fp16 before accumulating in fp32. ptxas also unrolled the loop twice (the counter steps by 2 up to 0x200 = 512).

2560 instructions against 16 for the same arithmetic. The runtime ratio is 5.4×, not 160×, because the TC kernel is no longer limited by math instructions. It is limited by its loads and the operand traffic around them.

PyTorch: cuBLAS on tensor cores

Eager PyTorch launches ampere_fp16_s1688gemm_fp16_128x128_ldg8_f2f_stages_32x1_nn (213.31 µs), then a generic copy kernel (unrolled_elementwise_kernel<direct_copy_kernel_cuda…>, 28.58 µs) for .float(). Under torch.compile, the matmul is still extern_kernels.mm (215.3 µs), and the conversion becomes the Triton kernel triton_poi_fused__to_copy_0 (17.79 µs). Its TTIR, PTX and SASS are in the tabs. The cuBLAS kernel name reads, by cuBLAS's naming convention: an Ampere kernel (reused on Ada), fp16 inputs, "s1688" = fp32 accumulation with an m16n8k8 MMA shape, fp16 output, 128×128 block tile, 8-element (16-byte) global loads, and a multi-stage pipeline. We have no SASS for it in the captures, so take that decoding as a reading of the name. The structure it implies (shared-memory staging, 16-byte loads, pipelining) is exactly what tinygrad's hand-coded kernel lacks.

The two results are not numerically identical. (a @ b).float() rounds each output to fp16 first: at magnitudes around 256, the largest in this example, consecutive fp16 values are 0.25 apart. tinygrad's matmul(b, dtype=float) stores the fp32 accumulator directly, with no conversion kernel.

What to remember

  • On sm_89, a tensor core op is mma.sync.m16n8k16: a warp-wide, synchronous, register-to-register instruction doing 2048 multiply-adds. In SASS it is HMMA.16816.F32.
  • The 32 lanes hold fixed fragments: lane L has rows/columns L>>2 (+8) and 2·(L%4) (+1, +8). tinygrad encodes this as seven size-2 splits (cuda_tc_opts) and per-operand swizzles in tc.py.
  • The TC opt applies when the reduce is ADD over a MUL (optionally cast), the dtypes match a tensor core exactly, and the dims divide (or TC_OPT=2 pads). It must be the first opt. Then the heuristic adds a 4×4 upcast and 4 warps per block.
  • The WMMA UOp becomes a call to a generated __device__ function with inline PTX. NVRTC passes it through and ptxas emits HMMA.
  • tinygrad's hand-coded TC kernel loads fragments straight from global memory (no shared memory, no ldmatrix). It is 5.4× faster than CUDA cores and more accurate, and still 2.5× slower than cuBLAS's shared-memory pipeline.
