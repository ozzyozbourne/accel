Chapter 6

The optimizer: opts, heuristics, BEAM

The same one-line matmul, a @ b on two 1024×1024 fp32 matrices, ran in 37.24 ms, 686 µs or 224 µs on the L4 depending on one environment variable. Nothing upstream changed: the schedule, the AST and the fusion decisions are identical. What changed is a short list of opts that tinygrad applied to the kernel's loop nest. This chapter takes that list apart: what each OptOp does to the axes, how the kernel name encodes the result, how the hand-coded heuristic picks its opts, what BEAM search does instead, and why a 4×4 or 16×4 register tile is worth a 54–166× speedup.

The vocabulary: axes, AxisType and kernel names

By the time the optimizer runs, a kernel is a SINK whose loops are RANGE UOps (see chapter 2). For the matmul there are three: two output loops i, j and one reduce loop k. You can see them in the kernel AST as UOp.range(1024, 1, AxisType.WEAK), UOp.range(1024, 2, AxisType.WEAK) and UOp.range(1024, 0, AxisType.REDUCE). The second argument is the range's id and the third is its AxisType.

AxisType is defined in . The letters and colours tinygrad uses to print each type are at –. The sort position that orders axes is axis_to_pos at . The types a CUDA matmul uses:

The Scheduler (the optimizer's view of a kernel) lists the ranges sorted by (axis_to_pos, id) (). Two things depend on that order. Opt axis numbers count positions in it, and the kernel name is built from it (–). The name is r if the kernel has a REDUCE (E if it doesn't), followed by every axis size in that order, each printed in its type's colour. With colours off you only see the digits, so the order is what you have to remember: globals, warp, locals, upcasts, reduce, unroll.

So r_32_16_8_16_4_4_256_4 reads: 32·16 = 512 blocks, 8·16 = 128 threads per block, a 4×4 tile of outputs per thread (512·128·16 = 1024² outputs), and a reduce loop of 256 iterations that each do 4 values of k (256·4 = 1024). The decoder above is computed by replaying each capture's applied_opts, the same way the next widget does, and checking that the result equals the captured name.

OptOps: the moves

An opt is a frozen dataclass Opt(op, axis, arg) (). There are ten ops (). Scheduler.apply_opt (–) turns each one into a rewrite of the AST. Six of them map to an AxisType through opt_to_at () and are implemented by a single primitive, shift_to (–):

def shift_to(self, rng, amount, new_type, top=False, input_new_rng=None):
  if (old_sz:=rng.src[0].divides(amount)) is None: raise KernelOptError(...)
  new_rng = UOp.range(amount, next(self.opt_range), new_type)        # a fresh range id
  replaced_rng = rng.replace(src=(old_sz,))                          # same id, smaller size
  sub_axis = (new_rng * old_sz + replaced_rng) if top else (replaced_rng * amount + new_rng)
  self.ast = self.ast.substitute({rng:sub_axis})

Every split replaces a range r of size N with r'·amount + new, where r' has size N/amount. The new sub-axis is the inner, stride-1 part of the old index, unless top=True, which makes it the outer part. Because the AST is rewritten, every INDEX that used r now uses the two-term expression, and later passes such as the expander and gpudims see two ranges instead of one. Opt order matters: the second split of an axis splits what the first one left over (r'), so the first opt applied to an axis owns its fastest-varying bits.

Elsewhere in the book you have seen GROUPTOP(0,16) on row sums (r_1024_16_64, chapter 5) and UPCAST(0,4) plus LOCAL(0,32) on a + b (E_8192_32_4, chapter 1). The matmul uses UPCAST, UNROLL, LOCAL and, under BEAM, SWAP.

Inside hand_coded_optimizations

With no BEAM and no NOOPT, apply_opts (–) calls hand_coded_optimizations in . This is a fixed sequence of rules, each guarded by a condition on the kernel. Here is the sequence for our matmul, in source order, with the decision each step made:

  1. Tensor cores (–). It tries Opt(TC, axis, …) for axes 0–2. The inputs are fp32, and the only fp32 tensor core on sm_89 is TF32, which CUDA skips unless ALLOW_TF32=1 (). Every attempt raises, so the step does nothing. Chapter 7 shows the fp16 case, where this step succeeds and returns early.
  2. Matvec (–). This step requires the second buffer's index to contain every range the first one uses. A's index uses i, B's doesn't, so it is skipped.
  3. Grouping (). Only for outputs of at most 2048 elements. Ours has 1M, so it is skipped.
  4. Masked upcasts (–). There are no WHERE gates, so nothing happens.
  5. The upcast loop (–). While the output is ≥ 1024 elements and fewer than 32 values are upcast, it considers each output axis that some buffer does not index (an axis along which that buffer is broadcast). Upcasting such an axis lets that buffer's value be reused across the upcast registers. Both i (B ignores it) and j (A ignores it) qualify. Candidates are sorted by (number of buffers using the axis, sum of its strides): i has strides 1024 in A and in C (sum 2048), j has stride 1 in B and in C (sum 2). So UPCAST(1,4) (on j) comes first, then UPCAST(0,4) (on i). With both axes upcast there is no candidate left and the loop stops at 16 values.
  6. Unroll the reduce (–). K = 1024 is larger than 32, so it unrolls by 4: UNROLL(0,4).
  7. Default float4 upcast (). Skipped, because something is already upcast.
  8. Locals (–). It ranks global axes, broadcast axes first, then higher axis first. Axis 1 gets the first size from [16, 8, 4, 3, 2] that divides it (only axis 0 may also try 32): 16. Axis 0 then gets the largest size that keeps the block at most 128 threads: 8. They are applied in axis order: LOCAL(0,8), LOCAL(1,16).
  9. Threads (). CPU only.

The result is exactly the captured list: UPCAST(1,4), UPCAST(0,4), UNROLL(0,4), LOCAL(0,8), LOCAL(1,16). None of it was timed. The heuristic is a handful of rules of thumb (broadcast axes are good to upcast, blocks of 128 threads, a float4-friendly unroll of 4), and it produced a kernel 54× faster than NOOPT. The fp16 matmul in chapter 7 with TC=0 goes through the same steps and ends up with r_64_32_8_16_4_4_512_4: the same opts on a 2048³ problem.

In the stepper, flatten range is the first snapshot after the opts were applied (get_optimized_ast runs it, ). The AST now has eight ranges with types GLOBAL, LOCAL, UPCAST, REDUCE and UNROLL. Step to expander: the UPCAST and UNROLL ranges disappear and become vectors of constants. Then step to add gpudims: GLOBAL and LOCAL become SPECIAL uops.

Register tiling: why 4×4 is fast

The NOOPT kernel makes each thread compute one output C[i][j]. For every k it loads A[i][k] and B[k][j] and does one multiply-add: two loads per FFMA. The GPU can issue FFMAs far faster than its load path can supply operands, so this kernel spends its time waiting for loads.

UPCAST changes the shape of a thread's work. With i and j both upcast by 4, a thread owns a 4×4 tile of C held in 16 registers. At each k it loads four values of A (one column slice of its 4 rows) and four of B (one row slice of its 4 columns), and performs the 16 multiply-adds of their outer product. That is 8 loads for 16 FFMAs. BEAM's kernel upcasts i twice (16 rows) and j once (4 columns): 20 loads for 64 FFMAs. Step through it:

The NOOPT kernel uses 47 registers for a single accumulator: ptxas unrolled its scalar loop 16 times (the counter steps by 0x10 up to 0x400), so its loop body holds 32 scalar LDG.E for 16 FFMAs. BEAM's 64 accumulators need 128 registers, with 256 FFMAs and 32 loads per iteration (16 LDG.E.128 for A, 16 scalar LDG.E for B).

tinygrad's own cost estimate (estimates.lds in the capture: bytes moved by all load and store instructions, summed over all threads) tells the same story at whole-kernel scale:

The last column is far above the L4's 300 GB/s of DRAM bandwidth. The inputs are only 8 MB, so most of these loads hit in the 48 MB L2 or the per-SM L1, and DRAM traffic is a small fraction. None of these kernels uses shared memory (there is no __shared__ and no BAR in the SASS): all data reuse comes from registers and the caches. What limits them is how many load instructions the SMs can issue and how fast the caches answer, and a register tile cuts both.

Register tiling costs registers. With 128 registers per thread, an SM's 64K-register file holds at most 512 of BEAM's threads, versus 1536 threads at 40 registers or fewer. Fewer resident warps means less latency hiding. The tradeoff is exactly the kind of thing that is hard to predict and easy to measure, which is the case for BEAM.

From axes to blockIdx and threadIdx: gpudims

The opts decide which axes are GLOBAL and LOCAL. The pass add gpudims () turns them into hardware indices. add_gpudims (–) does four things:

  1. It collects global dims (GLOBAL and THREAD ranges) and local dims (WARP, LOCAL and GROUP_REDUCE ranges), sorted by range id ().
  2. It makes SPECIAL uops for them through get_grouped_dims (). If there are more than three dims, or one exceeds the hardware limit, it first tries to merge adjacent dims and otherwise splits a dim by its smallest factor. Then it rebuilds each original index from the flat id with // and %. The CUDA limits are global_max = (2147483647, 65535, 65535) and local_max = (1024, 1024, 64) ().
  3. Globals are passed with reverse=True (), so the last global axis becomes blockIdx.x. Locals keep their order: the first local is threadIdx.x.
  4. It replaces each RANGE with its index (–). If a global store does not use some local range, it also adds a lidx==0 mask, which is where the if (lidx0==0) of grouped reductions comes from.

The renderer prints a SPECIAL as int gidx0 = blockIdx.x; /* 16 */ (code_for_workitem, ), and __launch_bounds__ is the product of the local sizes (). ProgramInfo.from_sink then reads the SPECIALs to fill global_size and local_size (–). Note that global_size is the number of blocks, the CUDA grid, not the total number of threads.

This reversal is why the heuristic kernel's name starts with 32_16 while its grid is 16 × 32: g0 (32, rows) became blockIdx.y and g1 (16, columns) became blockIdx.x. In the source, gidx0 = blockIdx.x; /* 16 */ appears in alu0 = ((gidx0<<6)+(lidx1<<2)), the column offset. BEAM's SWAP(0,1) flips this: its rows are on blockIdx.x (gidx0<<17 = 128 rows × 1024).

The map shows what one block computes, coloured by warp, with the hovered thread in white. Under the heuristic, a block covers 32 rows × 64 columns and each thread a compact 4×4 square. Lanes 0–7 of a warp (threadIdx.x) are 4 rows apart and read the same float4 of B (B does not depend on the row). Lanes 8 apart (threadIdx.y) read neighbouring float4s of B. Under BEAM, a block covers 128 rows × 64 columns, and each thread owns 16 rows spaced 8 apart × 4 columns spaced 16 apart. Here 16 consecutive lanes read 16 consecutive floats of B, one coalesced 64-byte access per load instruction, which is why BEAM's B loads can be scalar LDG.E without being slow.

Why NOOPT is 37 ms. With no LOCAL opt there are no local dims, so local_size is (1,1,1) and the source says __launch_bounds__(1): 1,048,576 blocks of one thread each. A warp is the unit of execution, so each block occupies a whole warp scheduler slot for one active lane. On top of that, the CUDA programming guide limits compute capability 8.9 to 24 resident blocks per SM, so at most 24 threads run per SM, out of 1536 thread slots. The kernel reaches 0.06 TFLOP/s.

BEAM search

Setting BEAM=2 replaces the heuristic with search. compile_linear stamps the beam width onto every kernel (pm_beam, , ). apply_opts then allocates real buffers for the kernel's arguments and calls beam_search with device access enabled (–). The search lives in :

  • Action space. A fixed list of 193 opts in this build (–): UPCAST by {0,2,3,4,5,7} on axes 0–7, UNROLL by {0,4,7} on axes 0–4, LOCAL by {2,3,4,8,13,16,29} on axes 0–5, GROUPTOP and GROUP variants, TC variants, every SWAP pair among axes 0–4, and THREAD. get_kernel_actions () tries each one on a copy of the Scheduler and keeps those that don't raise KernelOptError and stay within 256 upcast values and 1024 local threads.
  • A round. Every kernel in the current beam is expanded by every legal action (). The candidates are compiled in parallel worker processes by _try_compile (), which runs the full to_program pipeline and rejects kernels of 3000 uops or more. Candidates are deduplicated by compiled binary, so two opt lists that produce the same code are timed once (), and those estimated to need more than 1000× the least compute are dropped.
  • Timing. _time_program () runs each candidate up to 3 times on the real GPU and stops early once it is 3× slower than the current best. To keep this fast it shrinks the grid to at most 65536 blocks and scales the measured time back up (get_test_global_size, ). It also clears the L2 cache between runs when the device supports it.
  • Selection. Candidates are sorted by time, and the fastest amt (here 2) become the next beam. The search stops when the best time improves by less than BEAM_MIN_PROGRESS = 0.01 µs ().
  • Cache. The winning opt list is stored in tinygrad's disk cache under the AST's key, the beam width and the device (, ). The next run with the same kernel skips the search and just replays the opts. IGNORE_BEAM_CACHE=1 forces a new search.

Each round adds exactly one opt to each beam member, so the 7 opts in the capture mean the search ran seven rounds that each kept a faster kernel before it stopped. Because the actions are tried in a fixed order on top of each other, BEAM's opt lists look different from the heuristic's: it chose LOCALs before UPCASTs, and the previous sections showed what that does to the stride of each part. It also added a second UPCAST on i (its third UPCAST overall, 16 rows per thread) and a SWAP. FP32 tensor cores were in the action list too (TC), but they fail for the same TF32 reason as in the heuristic.

BEAM measures on the actual GPU, so its result depends on the hardware, the driver and the noise of the timing runs. Two searches can return different opt lists of similar speed. The capture is one run, on one L4. A BEAM result is also only as good as its action space: it cannot invent shared-memory tiling or software pipelining, which the hand-written cuBLAS kernel uses (see below). The DEBUG=2 output of a BEAM run prints one line per round with the best time and the colored_shape() of the leader.

How close to the L4's limits

NVIDIA's L4 datasheet lists 30.3 TFLOPS of fp32 at boost clock (58 SMs × 128 FP32 lanes × 2 FLOPs per FMA × 2.04 GHz). That is an upper bound; the clock under load can be lower. Dividing 2·1024³ FLOPs by each time:

The heuristic reaches about 10% of peak, BEAM about 32% and cuBLAS about 48%. A matmul's arithmetic intensity at the DRAM level is high (2·1024³ FLOPs over 12 MB of compulsory traffic, ≈ 170 FLOP/byte, above the L4's balance point of roughly 30.3 TFLOP/s ÷ 300 GB/s ≈ 100 FLOP/byte), so in principle it is compute-bound. In practice these kernels are bound by the load path between the caches and the registers, as computed above. The way forward is the one cuBLAS takes: stage tiles of A and B through shared memory, so that each global load feeds a whole block rather than one thread, and overlap those loads with the math.

PyTorch does no code generation for this. Eager mode calls cuBLAS, and the profiler shows ampere_sgemm_128x64_nn. The name is cuBLAS's own: an Ampere-generation SIMT (non-tensor-core) sgemm kernel, which by its name uses a 128×64 tile, reused here on the Ada L4. The fp32 matmul stays on FFMA because PyTorch keeps TF32 off for matmuls by default. Inductor does the same: extern_kernels.mm(arg0_1, arg1_1, out=buf0) in the output code. We have no SASS for cuBLAS in the captures, so the shared-memory claim above comes from how such kernels are generally built, not from this capture.

What to remember

  • The optimizer edits the loop nest of a kernel AST. Every opt except TC, PADTO, SWAP and NOLOCALS is one shift_to: it splits an axis into outer·amount + inner and gives the inner part a new AxisType.
  • AxisType decides what an axis becomes: GLOBAL → blockIdx, LOCAL → threadIdx, UPCAST → registers, REDUCE → the loop, UNROLL → straight-line loop body. The kernel name lists the axis sizes in that order.
  • Opt order sets the strides: the first split of an axis owns its stride-1 part. That decides whether a thread's values are adjacent (float4 loads) or a warp's lanes are adjacent (coalesced loads).
  • The heuristic is a fixed, untimed recipe: TC if possible, else upcast broadcast axes, unroll the reduce by 4, and add locals up to 128 threads. BEAM times real candidates on the GPU and caches the winning opt list.
  • Register tiling turns 2 loads per FFMA into 0.31 (BEAM) by reusing every loaded value across a tile of accumulators: 37.24 ms → 686 µs → 224 µs. cuBLAS still wins at 149 µs.
