Chapter 1

The journey of a + b

We follow a single elementwise add of two 1024×1024 float32 tensors through every stage of tinygrad on an NVIDIA L4: the lazy graph, the scheduler, each named compiler pass, the kernel name E_8192_32_4, CUDA C, PTX, the 19 SASS instructions the GPU runs, and the launch of 8192 blocks. Then we watch PyTorch do the same add twice, once with a prebuilt kernel and once with a Triton kernel it writes on the fly, and compare the machine code. Later chapters zoom in on each stage. This one is the map.

Fourteen characters of Python

Here is the program, as the capture harness ran it (harness/examples.py):

from tinygrad import Tensor
a = Tensor(np_a).realize()      # 1024 x 1024 float32, copied to the L4
b = Tensor(np_b).realize()
c = a + b                       # builds a graph node; no GPU work
c.realize()                     # schedule -> codegen -> compile -> launch

The line c = a + b does not add anything. Tensor.__add__ () goes through _binop (), which promotes dtypes and calls alu(Ops.ADD, …). That wraps a new UOp in a new Tensor. A tinygrad Tensor is only a handle: its slots are uop, is_param and grad (). All the information lives in the UOp graph it points to. The capture printed that graph just before realize():

add/default · tensor_graph (pyrender of c.uop before realize)

  
Read it bottom up. c7 is the ADD. Its two sources are RESHAPEs of two BUFFERs. A buffer in tinygrad is always one-dimensional, here 1,048,576 floats on 'CUDA', and a RESHAPE whose shape is itself a UOp (c3, a STACK of two constants) gives it the shape 1024×1024. There is no stride, no view object and no ShapeTracker: tinygrad 0.14 keeps movement ops as ordinary nodes until the scheduler turns them into arithmetic. .realize() () is where the compiler starts.

Scheduling: from a graph to one kernel

  
The scheduler's job is to turn "a graph of tensor operations" into "a list of kernels, each a loop nest with loads and stores". For a + b the answer is obviously one kernel, but it goes through the same machinery as softmax (three kernels) or a matmul.

  
realize() calls linear_with_vars (), which runs two groups of passes:

  
    
    
  1. Callify (transform_to_call, ). number the uops tags the output. early transform tensor graph turns "the value of c" into "allocate a new buffer and STORE the ADD into it": that is the c4.after(c4.store(c9)) line in the journey. replace bufs swaps the concrete buffers for numbered PARAM slots 0, 1, 2. The output is slot 0. After this pass the graph no longer mentions which memory it runs on, so it can be cached and reused as a schedule.
    2. 
    
  2. Schedule (create_linear_with_vars, ), whose core is get_kernel_graph (). apply rangeify gives every node a tuple of RANGE loop variables. The output gets two fresh ranges, r0 (rows) and r1 (columns). Each RESHAPE pushes them back to its 1-D buffer as r0*1024+r1, and then the RESHAPE is deleted. stage to store and split kernels cut the graph at every STORE with no open loops. There is exactly one here, so there is one kernel.
    3. 
  

  
You can watch rangeify decide this with DEBUG_RANGEIFY=1. Run on the CPU against the NULL device (chapter 11 explains the trick), it prints one row per node: the number of consumers, the op, the shape, and the ranges the node is indexed with. *** marks nodes that must be materialized:

  
***  0 Ops.STORE            (1024, 1024)                         0 [r0][r1]
     1 Ops.ADD              (1024, 1024)                         0 [r0][r1]
     1 Ops.RESHAPE          (1024, 1024)                         0 [(r0*1024+r1)] -> [r0][r1]
     1 Ops.PARAM            (1048576,)                           0 [(r0*1024+r1)]
     1 Ops.RESHAPE          (1024, 1024)                         0 [(r0*1024+r1)] -> [r0][r1]
     1 Ops.PARAM            (1048576,)                           0 [(r0*1024+r1)]
     ...


  
Every value node (the ADD, the RESHAPEs, the input PARAMs) has exactly one consumer, so each one inherits its consumer's ranges and fuses into it (). Only the STORE starts new loops. Chapter 3 shows what happens when a node has two consumers that disagree, and the result is a second kernel.

This is the whole program in tinygrad's vocabulary. PARAM 0, 1 and 2 are the output and the two inputs, each a flat array of 1,048,576 floats. c3 and c5 are two loops of 1024 with axis type WEAK, meaning "an output loop that codegen may map to hardware however it likes". c6 = c3*1024+c5 is the flat index. c12 loads both inputs at that index and adds them (an INDEX stands for its load; explicit LOAD ops are added later). c14 stores to the output at the same index and ends both loops. The KernelInfo name is still 'test'.


  
Every pass, in order

  
From here to the CUDA source there are 52 named graph_rewrite passes in this capture: 4 on the tensor graph, 17 in the scheduler, 30 in codegen, and one on the runtime side. The stepper shows them all. Bar height is the graph size after each pass, and faded bars are passes that found nothing to do for a + b, which is most of them: there is no reduction, no shared memory and no exotic dtype. Click through the changed passes. The short description under the pass name comes from the source.

  

  
Notice where the node count jumps. devectorize2 takes the graph from 29 to 50 UOps because it splits the 4-wide vector into four scalar loads, adds and stores. add images, which is where memory_coalescing runs just before it (), takes it back down to 39 by gluing the four scalar loads into one 4-wide SHRINK load. casted consts adds a CAST for every constant. The interesting decisions, though, happen in a step that is not a named rewrite at all: apply_opts.


  
Choosing the launch shape: UPCAST 4, LOCAL 32

  
After simplify ranges has merged the two loops into one of 1,048,576 (, since r0*1024+r1 over a 1024×1024 range is just a counter), the optimizer decides how to map that loop onto the GPU. apply_opts () first turns the WEAK range into a GLOBAL one (convert_loop_to_global, ), then runs the hand-coded heuristics. The capture records what they chose:

  
applied_opts = (Opt(op=OptOps.UPCAST, axis=0, arg=4), Opt(op=OptOps.LOCAL, axis=0, arg=32))


  
Every opt is a call to shift_to (). It splits a range of size N into an outer range of N/amount and a new inner range of size amount with a new axis type, and substitutes old → outer*amount + inner everywhere. Step through it:

  

  
Why UPCAST 4? An UPCAST axis is not a loop at runtime. Each thread does all of its iterations, so the four consecutive floats become one 16-byte vector. Running DEBUG=4 against the NULL device shows where it came from: the heuristic printed more upcast axis : [(0, 3, 0, 4)]. That is the upcast loop in , whose tuples are (num_strides, sum_strides, axis, amount). The loop is meant to find axes that some buffer broadcasts over (stride 0), the classic case being the M and N axes of a matmul. It qualifies an axis when the range is not in a buffer index's backward_slice. Here every index is the bare range, and backward_slice excludes the node itself (), so all three buffers pass the test. Upcasting by 3 does not divide 1,048,576, so the only candidate is 4. On the next iteration the axis is already upcast and the loop stops. We checked this by instrumenting the heuristic on the CPU: all three indices are the range itself. If the loop had not fired, the fallback a few lines later (, "if nothing at all is upcasted… do an upcast" by 4) would have produced the same opt.

  
Why LOCAL 32? The locals step () tries sizes from [32]*(axis==0) + [16, 8, 4, 3, 2] and keeps the first one that divides the axis while the total stays ≤ 128 (). Axis 0 gets first pick and 32 divides 262,144, so each block has 32 threads: exactly one warp. That is a small block, and we come back to the cost at the end of the chapter.


  
Reading the name E_8192_32_4

  
get_optimized_ast () names the kernel from its axes: "r" if there is a reduction, else "E", then one number per axis in a fixed order (globals, then locals, then upcasts, then reduce and unroll axes), colored by axis type in the terminal.

  

    
PartAxis typeMeaning on the GPU

    
Eno REDUCEelementwise kernel

    
8192GLOBAL (blue)gidx0 = blockIdx.x: 8192 blocks in the grid

    
32LOCAL (cyan)lidx0 = threadIdx.x: 32 threads per block

    
4UPCAST (yellow)4 consecutive floats per thread, held in registers as one float4

  

  
8192 × 32 × 4 = 1,048,576, one entry per element of c. Every other contiguous elementwise example in the book (fused_chain, gelu, exp, sin, int_divmod) has the same 1,048,576 output elements, gets the same opts, and so has the same name. Only the body differs. The colors survive in the IR as ANSI escapes inside KernelInfo(name='E\x1b[90m_\x1b[0m\x1b[34m8192…'), which is why the pass stepper shows them. The function name in C is stripped of them (function_name).


  
From loops back to hardware

  
The remaining codegen passes "lower" the optimized graph until each UOp corresponds to one statement of C. Use the pass stepper above to see each of these:

  
    
    
  • postopt symbolic simplifies (g*32+l)*4+u to g*128 + l*4 + u.
    • 
    
  • expander () removes the UPCAST range. In its place is a vector constant STACK(0, 1, 2, 3), so the index becomes a 4-wide vector and so does every value computed from it. The loop over 4 is now data parallelism inside one thread.
    • 
    
  • add gpudims () replaces the GLOBAL range with UOp.special(8192, 'gidx0') and the LOCAL range with UOp.special(32, 'lidx0'). These SPECIAL ops will render as blockIdx.x and threadIdx.x.
    • 
    
  • *** expand broadcast / add loads inserts explicit .load()s. devectorize2 splits every 4-wide op into four scalars (), and memory coalescing regroups the four scalar loads at base+0..3 into a single 4-wide SHRINK load. It can do that because the base is a multiple of 4, which is what lets the CUDA renderer emit a float4.
    • 
    
  • lower all index dtypes commits the abstract weakint index type to 32-bit int, since 1,048,576 fits.
    • 
    
  • late decompositions rewrites multiplications by powers of two as shifts: gidx0*128 becomes gidx0<<7 and lidx0*4 becomes lidx0<<2.
    • 
    
  • linearize/render toposorts the graph into 47 uops, prints the C, and calls the compiler.
    • 
  


  
The linear program and the CUDA C

  
Here are all the stages of the finished kernel in one place. Start with the Source tab:

  

  
Each line of C maps to a few uops. int gidx0 = blockIdx.x; /* 8192 */ is SPECIAL uop 7, with its bound in a comment. alu0 = ((gidx0<<7)+(lidx0<<2)) is uops 17 to 19: two SHLs and an ADD. It gets a name because three loads and stores use it, and single-use expressions are inlined. The two float4 loads are the SHRINK + LOAD pairs at uops 20 to 23. The make_float4 store at the end is uops 26 to 44: eight INDEXes pick lanes out of the two float4s, four ADDs add them, then a STACK rebuilds the vector, and a SHRINK and a STORE write it. The prefix (typedef unsigned int uint, INFINITY, tg_bitcast) is emitted for every CUDA kernel. __launch_bounds__(32) is the product of the local sizes (), and it tells the compiler no block will ever have more than 32 threads.

  
In the Linear uops tab you can see the effect of casted consts: every constant appears as a CONST weakint plus a CAST int, for example uops 5 and 6 (8192). The small constants near the end (0, 1, 3, plus the 2 reused from uop 12) are lane numbers inside the float4.


  
PTX and SASS

  
On the CUDA device, tinygrad's compiler is NVRTC (), called with --gpu-architecture=sm_89, CUDA -I include paths and, on new versions, --minimal (), and asked for PTX, not a cubin. Switch the widget to PTX. PTX is a virtual ISA with unlimited typed registers (%r 32-bit integer, %rd 64-bit, %f float). NVVM has already done real work on it:

  
    
    
  • shl.b32 %r3, %r1, 7 and shl.b32 %r4, %r2, 2 are tinygrad's shifts. mul.wide.s32 %rd7, %r5, 4 turns the element index into a 64-bit byte offset.
    • 
    
  • ld.global.v4.f32 {%f1, %f2, %f3, %f4}, [%rd8] is the float4 load, still one instruction.
    • 
    
  • The four add.f32 and one st.global.v4.f32 are the add and the store.
    • 
  

  
tinygrad passes this PTX to cuModuleLoadData, and the driver's ptxas JIT compiles it to SASS for the exact GPU, which here is sm_89. To show you that SASS, the capture harness compiled the same PTX with ptxas -arch=sm_89 -v and disassembled it with cuobjdump -sass. Switch to SASS. Without the padding NOPs, the whole kernel is 19 instructions:

  
/*0000*/  MOV R1, c[0x0][0x28] ;                       // stack pointer (unused here)
/*0010*/  S2R R0, SR_CTAID.X ;                         // R0 = blockIdx.x          (gidx0)
/*0020*/  MOV R7, 0x4 ;                                // sizeof(float)
/*0030*/  ULDC.64 UR4, c[0x0][0x118] ;                 // global memory descriptor for .E accesses
/*0040*/  S2R R3, SR_TID.X ;                           // R3 = threadIdx.x         (lidx0)
/*0050*/  LEA R0, R0, R3, 0x5 ;                        // R0 = (gidx0 << 5) + lidx0
/*0060*/  SHF.L.U32 R6, R0, 0x2, RZ ;                  // R6 = R0 << 2  == alu0
/*0070*/  IMAD.WIDE R2, R6, R7, c[0x0][0x168] ;        // &data1[alu0] = alu0*4 + param 1
/*0080*/  IMAD.WIDE R4, R6.reuse, R7.reuse, c[0x0][0x170] ; // &data2[alu0]
/*0090*/  LDG.E.128 R8, [R2.64] ;                      // float4 val0 -> R8..R11
/*00a0*/  LDG.E.128 R12, [R4.64] ;                     // float4 val1 -> R12..R15
/*00b0*/  IMAD.WIDE R6, R6, R7, c[0x0][0x160] ;        // &data0[alu0]  (param 0: the output)
/*00c0*/  FADD R11, R11, R15 ;                         // .w
/*00d0*/  FADD R10, R10, R14 ;                         // .z
/*00e0*/  FADD R9, R9, R13 ;                           // .y
/*00f0*/  FADD R8, R8, R12 ;                           // .x
/*0100*/  STG.E.128 [R6.64], R8 ;                      // one 16-byte store
/*0110*/  EXIT ;
/*0120*/  BRA 0x120;                                   // never reached: padding loop


  
(The comments are ours. The instructions are the capture's.) Some things to notice:

  
    
    
  • ptxas refactored tinygrad's index. tinygrad emitted (gidx0<<7)+(lidx0<<2). ptxas factored it as ((gidx0<<5)+lidx0)<<2, a single LEA (shift-and-add) followed by one shift. Same value, one instruction fewer.
    • 
    
  • Kernel parameters live in constant bank 0. c[0x0][0x160], 0x168 and 0x170 are the three 8-byte pointers, in argument order data0, data1, data2. ptxas reports 376 bytes cmem[0]: 0x160 = 352 bytes of driver-reserved space, plus 3 × 8 bytes of parameters.
    • 
    
  • .E.128 is a 128-bit access through the 64-bit address register pair R2.64 (R2:R3). One instruction moves a whole float4 per thread, and 512 bytes per warp.
    • 
    
  • 18 registers (ptxas -v: Used 18 registers, used 0 barriers, 376 bytes cmem[0]), no stack and no spills.
    • 
  

  


  
Who touches what: blocks, warps, threads

  
The launch is 8192 blocks of 32 threads. Each block is one warp, the 32 threads that the SM runs in lockstep. Every thread runs the 19 instructions above with its own (gidx0, lidx0) and computes alu0 = (gidx0<<7)+(lidx0<<2). Pick a block and a thread below, or press run warp to watch one warp execute its load, add and store. The memory strip shows the 128 floats (512 bytes) that this block covers, in rows of 32 floats. One row is 128 bytes, the size of an L2 cache line on NVIDIA GPUs.

  

  
This is the best access pattern a GPU memory system can get. The 32 threads of a warp ask for 32 adjacent 16-byte pieces, 512 contiguous bytes, so each LDG.E.128 is served as four full cache lines and no byte is fetched twice. Block g starts exactly where block g-1 ended (g×128 floats), so the 8192 blocks tile the 4 MB arrays with no gaps or overlaps. Row and column never appear: the 2-D shape vanished in simplify ranges, and element (i, j) is just float number 1024·i + j.


  
Launch and timing

  
The runtime side is short. exec_kernel () gets the compiled program, computes the launch dimensions from the ProgramInfo (), and calls CUDAProgram.__call__. That packs the three device pointers into a 24-byte struct and launches:

  
# tinygrad/runtime/ops_cuda.py:65
cuLaunchKernel(self.prg, *global_size, *local_size, self.smem, None, None, self.vargs)
#               E_8192_32_4  8192,1,1     32,1,1     0 bytes   default stream, args via 'extra'


  
Note that tinygrad's global_size is the number of blocks (gridDim), not the number of threads as in OpenCL. With DEBUG=2, every launch is bracketed by two CUDA events and synchronized (), and the elapsed time is printed. The harness took the best of five runs: 21.57 µs.

  
The kernel reads two 4 MiB arrays and writes one: 12,582,912 bytes, which is the mem estimate the capture recorded. 12,582,912 B / 21.57 µs = 583 GB/s. That is almost twice the L4's DRAM bandwidth (300 GB/s on NVIDIA's datasheet), which looks impossible until you remember that the L4 has a 48 MB L2 cache. The harness timed five back-to-back runs on the same inputs, so the 12 MB working set was already in L2. Treat these numbers as "hot cache" numbers: a fair comparison between implementations measured the same way, not a statement about DRAM.

  

  
The PyTorch kernels are three times faster. Before reading anything into that, note that the two sides were measured differently. PyTorch's times are kernel durations from the profiler (CUPTI). tinygrad's come from events recorded on the stream around a single launch, which also counts the gap between the first event and the kernel starting. For a kernel this short, that overhead is a large share of the total. The block size may also cost some real time. With only 32 threads per block, and CUDA's limit of 24 resident blocks per SM on compute capability 8.9, an SM can hold at most 768 of these threads, half of its 1536 thread slots (the max_threads_per_multi_processor=1536 in Inductor's device properties below). The capture cannot separate the two effects. Chapter 6 shows how BEAM search explores other launch shapes.


  
The same add in PyTorch

  
Eager mode launched one kernel, and the profiler gave its full name:

  

  
vectorized_elementwise_kernel<4, CUDAFunctor_add<float>, …> is a C++ template instantiated for float addition, with vector width 4, and compiled into libtorch_cuda.so when PyTorch was built. No code is generated at run time. The template already contains the same idea tinygrad's heuristic found: four elements per thread, loaded as a vector. Its cost appears with longer expressions. Each eager op is a separate kernel that reads and writes all of memory, so fused_chain launches four of these (see the table in the preface).

  
torch.compile runs the other pipeline. Step through the tabs from FX graph to SASS:

  

  
    
    
  • FX graph: Dynamo plus AOTAutograd reduced the lambda to one torch.ops.aten.add.Tensor.
    • 
    
  • Inductor IR: a SchedulerNode with a loop body: load, load, add, store. Before fusion the index is 1024*p0 + p1 over two ranges. After fusion it is one range c0 of 1,048,576. That is the same simplification tinygrad's simplify ranges made.
    • 
    
  • Output code: a Python module with the kernel triton_poi_fused_add_0 ("poi" for pointwise), written in Triton. One Triton program handles XBLOCK elements: xindex = xoffset + tl.arange(0, XBLOCK). The code says nothing about threads. The call() function at the bottom allocates buf0 and launches the kernel.
    • 
    
  • TTIR → TTGIR: Triton's whole-tensor IR (tensor<1024xf32>) gains a layout in TTGIR: #blocked<{sizePerThread = [4], threadsPerWarp = [32], warpsPerCTA = [4]}>. That line plays the role of tinygrad's UPCAST 4 and LOCAL 32: 4 contiguous elements per thread, 32 threads per warp, 4 warps per program.
    • 
    
  • LLVM IR → PTX → SASS: LLVM's NVPTX backend emits the PTX, and Triton runs ptxas itself to produce a cubin.
    • 
  

  
Inductor autotuned two configurations of this kernel, and the capture kept both (use the selector in the TTIR to SASS tabs). With 4 warps and XBLOCK=1024, each of 128 threads handles 8 floats as two float4s, 512 floats apart, and uses 26 registers. With 8 warps and XBLOCK=512, each of 256 threads handles 2 floats with LDG.E.64 and uses 12 registers. The capture does not record which configuration the autotuner picked for the timed run.

  
Here are the two SASS listings side by side, tinygrad's 19 instructions and Triton's 4-warp variant:

  

  
The two compilers arrive at nearly the same machine code: the same S2R pair, the same IMAD.WIDE … c[0x0][…] address computations, 128-bit LDG.E.128 loads, FADDs and 128-bit stores. The differences are in the tiling. Triton's thread does two float4s per input (an extra +0x800 = 2048-byte offset on the second load, which is 512 floats), and its index needs a LOP3.LUT … 0x1fc to mask tid*4 to 0..508, because 128 threads × 4 = 512 covers only half of XBLOCK = 1024. tinygrad's block is a quarter the size, so its index math is two instructions, LEA and SHF, against Triton's three (SHF, LOP3, LEA). The real difference between the frameworks is not in this kernel. It is in what happens with longer expressions (chapter 3), reductions (chapter 5) and matmuls (chapters 6 and 7).


  
What to take from this chapter

  
    
    
  • A tinygrad Tensor is a lazy UOp graph. realize() starts a compiler.
    • 
    
  • The scheduler turns shapes into loops (RANGE) and movement ops into index arithmetic, then cuts the graph into kernels.
    • 
    
  • Codegen is a fixed sequence of named rewrite passes. Only the optimizer (apply_opts) makes choices: here UPCAST 4 and LOCAL 32, which give the name E_8192_32_4.
    • 
    
  • The UPCAST becomes a vector, the vector becomes a float4, and the float4 becomes ld.global.v4.f32 and then LDG.E.128. The LOCAL becomes threadIdx.x.
    • 
    
  • On the L4 the kernel runs in 21.57 µs, measured with events and on a hot L2. PyTorch's prebuilt kernel and its Triton kernel use the same float4 idea and nearly the same SASS.
