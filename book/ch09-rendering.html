Chapter 9

Rendering and compiling: CUDA C, PTX, SASS

After the last codegen pass, a kernel is still a graph. This chapter follows it the rest of the way: the linearizer orders the graph into a list, the renderer prints that list as CUDA C (or as PTX, with tinygrad's own assembly renderer), NVRTC turns C into PTX, and ptxas turns PTX into the SASS the L4 executes. We compare the two routes tinygrad offers, line by line, and see that they land on nearly the same machine code, then look at the third route PyTorch takes through Triton and LLVM.

From graph to list: linearization

Everything until now has been a graph_rewrite on a DAG of UOps. Text, though, is sequential. The first step of pm_to_program is do_linearize , which calls linearize(sink) . It is a toposort with priorities:

  • Each UOp gets a key (run_count, priority, extra). run_count is the product of the sizes of the loops it lives in, so code inside loops sorts later than code outside them.
  • The priority puts PARAMs first (ordered by slot), then buffers, and pushes LOADs early, STOREs late, RANGEs early and ENDs late .
  • A heap then emits UOps in that ideal order, but only once all their consumers are placed (it works from the SINK backwards and reverses the list at the end, ), so the result is always a valid topological order.

Then pm_linearize_cleanups does one structural rewrite on the list: a STORE with a gate becomes IF, STORE, ENDIF . That is the only way an if enters a tinygrad kernel. Here is the linear list for a + b, the kernel this chapter dissects. The columns are index, op, dtype, sources (by index) and arg:

Two details are worth noticing. Every constant appears as CONST of a weakint followed by a CAST to a real dtype: the casted consts pass spells every literal that way. And the vector load is SHRINK (4 elements starting at the index) then LOAD, followed by four INDEX uops that pick lanes 0..3 out of the loaded vector.

The CUDA C renderer

do_render hands the list to renderer.render . For the default CUDA device that is CUDARenderer , a subclass of the generic CStyleLanguage. Its _render loop walks the uops once and builds a dictionary from each UOp to a string. Each UOp is turned into text by a PatternMatcher (string_rewrite), the same machinery as every other pass, except that the rewrite produces strings instead of UOps.

The rules that shape what you see in every kernel of this book:

  • Names. PARAMs are named data{slot}_{size} . Other values get a prefix by op: val for loads, alu for arithmetic, cast, bidx, buf, wmma .
  • Inlining. A UOp gets its own variable only when it has to. Single-use ALU results, casts, and all INDEX/SHRINK address expressions are pasted into their consumer as text . That is why the add kernel has alu0 (used three times) but no variable for the sums. EXPAND_SSA=1 stops inlining single-use ALU, STACK and cast results (addresses are still inlined).
  • SPECIAL becomes blockIdx.x/threadIdx.x with the bound in a comment , using code_for_workitem .
  • Signature. extern "C" __global__ void __launch_bounds__(N) , where N is the product of the maxima of all local SPECIALs , i.e. exactly the block size. It lets ptxas budget registers for that block size.
  • Prefix. Every kernel starts with the same four lines: typedef unsigned int uint, INFINITY and NAN as bit patterns, and the tg_bitcast union template . Half, bfloat16 and fp8 add includes, vector structs and, for tensor cores, a WMMA wrapper around inline mma.sync (chapter 7).
  • Vectors. A 4-wide STACK becomes make_float4(...), a vector load is a cast to float4* and a dereference , and lanes are .x .y .z .w.
  • Gated loads become a C conditional (gate ? *ptr : alt) ; the gated store became an if during linearization.
  • Accumulators are register arrays (float buf0[1];) written through *(buf0+0), and RANGE becomes a for loop .

The sum_rows kernel shows most of these at once: register accumulators, two loops, shared memory with a barrier, and the gated final store.

And the padded slice from chapter 4 shows a gated load: the whole validity mask became the condition of a C ?:.

NVRTC and the compile cache

The source string goes to do_compile, which calls compiler.compile_cached(source) . For CUDA C that compiler is NVRTCCompiler, NVIDIA's runtime-compilation library loaded through ctypes. Its options are short :

self.compile_options = [f'--gpu-architecture={arch}']          # sm_89 on the L4
self.compile_options += ["-I/usr/local/cuda/include", "-I/usr/include", "-I/opt/cuda/include"]  # or CUDA_PATH
if (nvrtcMajor.value, nvrtcMinor.value) >= (12, 4): self.compile_options.append("--minimal")

No -use_fast_math, no -O flag (NVRTC optimizes by default), and floating-point contraction on, which is why the multiply-adds in previous chapters became FFMA. --minimal omits certain language features (texture and surface functions, the cudadevrt runtime functions) to cut compile time; tinygrad's kernels use none of them.

What comes back is PTX, not a binary: on the CUDA device the renderer creates the compiler with ptx=True , and compile calls nvrtcGetPTX . The last step to SASS happens when the runtime calls cuModuleLoadData on that PTX : the CUDA driver contains its own copy of ptxas and JIT-compiles for the GPU it finds. (The NV backend, which talks to the GPU without libcuda, asks NVRTC for a CUBIN instead.)

Where this book's SASS comes from. The driver's JIT output is not easy to dump, so the capture harness ran the standalone ptxas -arch=sm_89 -v on the exact PTX the driver received and disassembled the result with cuobjdump -sass. tinygrad does the equivalent at DEBUG=7 (cuda_disassemble: ptxas, then nvdisasm, ). The register counts quoted below are the ptxas -v lines in the "ptxas -v" tabs.

Caching. compile_cached looks the source string up in a SQLite database before compiling. The key is the full source text, the table is named after the compiler and arch (compile_cuda_sm_89_22, , plus the cache VERSION suffix ), and the database lives at ~/.cache/tinygrad/cache.db unless CACHEDB says otherwise . CCACHE=0 turns it off . Above it sits an in-memory cache keyed on the AST, renderer and every config variable that changes code generation (to_program_cache, ), so a kernel seen before in the same process skips all of codegen, not just the compile.

Line by line: C, PTX and SASS

Here is the add kernel in all three languages, from the captures. Hover a line of the CUDA C to see the PTX and SASS it became; hover a PTX or SASS line to go the other way. Switch routes to compare with tinygrad's own PTX renderer, which the next section introduces. I built the correspondence by hand by reading the registers through each listing.

Things to look for, NVRTC route first:

  • Parameters live in constant memory. PTX loads them with ld.param.u64. In SASS there is no load at all: kernel arguments sit in constant bank 0 starting at offset 0x160 on this architecture, and an instruction can read c[0x0][0x160] directly as an operand. data0 is c[0x0][0x160], data1 0x168, data2 0x170, 8 bytes each. That is also why ptxas reports 376 bytes cmem[0] here: 0x160 + 3·8 = 376. The two-argument exp kernel of chapter 8 reports 368.
  • Special registers. %ctaid.x and %tid.x become S2R R0, SR_CTAID.X and S2R R3, SR_TID.X, reads of per-thread system registers.
  • Address arithmetic gets fused. shl, shl, add, mul.wide become LEA, SHF.L.U32 and one IMAD.WIDE per pointer, which computes the 64-bit base + index·4 in one instruction with the base taken straight from the constant bank. The cvta.to.global conversions vanish.
  • Vectors become register quads. ld.global.v4.f32 {%f1, %f2, %f3, %f4} is LDG.E.128 R8, which writes R8, R9, R10 and R11. The four FADD leave their results in R8..R11, and STG.E.128 [R6.64], R8 stores the quad. .E means a 64-bit address; ULDC.64 UR4, c[0x0][0x118] loads the memory descriptor those instructions use implicitly.
  • Housekeeping. MOV R1, c[0x0][0x28] initializes the stack pointer (unused here), EXIT ends the thread, and BRA to its own address plus the trailing NOPs are padding that is never executed.

The SASS listing hides the other half of each instruction: the control bits. Every 128-bit SASS instruction carries scheduling information that ptxas computes (stall cycles, barrier indices for variable-latency results like loads, register reuse hints). cuobjdump shows only the reuse hints, as the .reuse suffix in IMAD.WIDE R4, R6.reuse, R7.reuse, c[0x0][0x170] above: the operand collector may keep R6 and R7 for the next instruction instead of reading the register file again. Choosing those bits and the instruction order is the part of ptxas that has no counterpart in the PTX.

tinygrad's own PTX renderer

tinygrad can skip C altogether. DEV=CUDA:PTX picks the second renderer registered for the CUDA device ([CUDARenderer, PTXRenderer, NVCCRenderer], ; selection by name in ). PTXRenderer prints PTX assembly from the same linear uops, and its "compiler" is a text substitution: PTXCompiler.compile replaces TARGET with the arch and VERSION with the PTX ISA version (7.8 for sm_89) . No NVRTC is involved; the driver's ptxas does all the compiling.

The two are recognizably the same program, written by very different authors:

  • Register names. NVVM numbers registers per type (%r5, %f17, %rd8). tinygrad names them %{prefix}_{type}_{n} after the UOp that made them, %alu_f32_0, %val_f32_4, %bidx_u64_1 (the ssa helper, ), and SPECIALs keep their names, %gidx0 and %lidx0. Both are virtual registers: PTX has unlimited registers, and ptxas does the real allocation.
  • No optimization. Every CAST of a CONST becomes a mov, even ones nothing reads: mov.b32 %cast_s32_0, 1048576 is the buffer size from the PARAM, and %cast_s32_5..8 are the lane indices 0..3 of the INDEX uops. Every INDEX recomputes its address with cvt.s64.s32 and mad.lo.s64 addr, idx, 4, base .
  • MULACC. PTXRenderer lists MULACC among its ops, so the late decompositions fused (gidx0<<7) + … into mad.lo.s32 %alu_s32_1, %gidx0, %cast_s32_4, %alu_s32_0, a multiply by 128 and an add in one instruction (). The C renderer does not list MULACC and leaves fusion to the compiler.
  • .maxntid 32 plays the role of __launch_bounds__(32) .

The results:

For add the difference is noise: 22.46 vs 22.53 µs. ptxas threw away the dead movs and fused the address math; the switch above shows the only real difference, 24 instructions instead of 19 and 20 registers instead of 18. The five extra instructions handle the 64-bit sign extension: SHF.R.S32.HI R0, RZ, 0x1f, R6 makes the high word of the index, SHF.L.U32 R17, R0, 0x2 scales it by 4, and one IADD3 per pointer adds it into the high half of the IMAD.WIDE.U32 result. That is needed because tinygrad's PTX says cvt.s64.s32 then a 64-bit multiply-add, while NVVM used mul.wide.s32, which ptxas maps onto IMAD.WIDE directly.

Where the routes diverge: sum_rows

The reduction shows a bigger gap: 25.54 vs 27.65 µs, and 361 vs 1001 lines of SASS for the same 64-iteration loop.

Both versions were fully unrolled by ptxas (64 LDG.E each). On the left, all 64 loads share one base register: LDG.E R62, [R2.64+0x4], [R2.64+0x8], … with the offset folded into the instruction. On the right, every load has its own index add (IADD3 R74, R4, 0x1), SHF.R.S32.HI, IMAD.WIDE.U32, SHF.L.U32 and another add for the high word. The reason is integer semantics. In C, signed overflow is undefined, so NVVM may assume (lidx0<<6)+Ridx0+(gidx0<<10) never wraps and turn base + 4·(i + k) into (base + 4·i) + 4·k. tinygrad's PTX computes the index with 32-bit mad.lo.s32/add.s32, which is defined to wrap modulo 2^32, then sign-extends with cvt.s64.s32. ptxas must honour the wrap, so it cannot pull the constant out, and it rebuilds the 64-bit address for every element.

The tinygrad PTX itself is shorter (76 lines vs NVRTC's 204) because it keeps the loops as loops: a RANGE becomes mov ridx, -1; bra END; LOOP: …; END: add 1; setp.lt; @p bra LOOP , and the gated store is @!%alu_pred_0 bra IF_… around the st.global . All the unrolling happened in ptxas.

matmul: the association of floating-point sums

The matmul kernel shows a subtler difference, and it is not in the PTX renderer. 684.03 vs 690.18 µs, 56 registers each, but the inner loop's float math differs: 64 FFMA via CUDA C, versus 48 FFMA + 16 FMUL + 16 FADD via tinygrad PTX.

In the uops, each accumulator update is acc + (a0·b0 + a1·b1 + a2·b2 + a3·b3): the four products are summed first and then added to the accumulator. tinygrad's PTX renders exactly that, and after MULACC fusion it is one mul.f32, three fma.rn.f32 and an add.f32 into %reg_f32_0. The C renderer, though, strips parentheses from nested additions and prints ((*(buf0+0))+(val3.x*val7.x)+(val3.y*val4.x)+…). C parses that left to right, as (((acc + a0·b0) + a1·b1) + …), which is a different association, and one that NVVM can contract into four FFMAs chained through the accumulator. Floating-point addition is not associative, so neither compiler may change the order the text gives it. The two kernels compute slightly different sums: the largest errors against numpy are 2.29e-4 (C) and 1.53e-4 (PTX), both well inside the tolerance.

The time difference is under 1%, because this matmul is limited by its loads, not by the 50 extra instructions per iteration (134 vs 84 in the inner loop: 16 more float ops, the rest 64-bit address math).

The lowering ladder

To close the tinygrad side, follow single pieces of the add kernel down all four levels. Each strand starts as linear uops, becomes a C expression, then PTX, then SASS. Press play to watch them descend, or pick a strand.

The ratio of lines changes in both directions. Index math expands from C to PTX (one C line, four PTX instructions) and contracts again in SASS (two instructions). Loads and stores keep a near one-to-one shape, because memory operations are what the program is about and no compiler may drop or merge them freely. The adds map one to one all the way down. Overall, 47 uops became 6 lines of C body, 23 PTX instructions and 19 SASS instructions.

PyTorch's route: Triton, MLIR and LLVM

torch.compile reaches the same hardware by a third road. Inductor writes a Triton kernel in Python; Triton parses it to TTIR (an MLIR dialect of tensor ops), lowers that to TTGIR, which assigns a layout saying which thread owns which elements, then to LLVM IR, and LLVM's NVPTX backend prints PTX. ptxas finishes the job, as in tinygrad.

The add kernel at each Triton stage:

  • In TTGIR the tensor of 1024 offsets gets the layout #ttg.blocked<{sizePerThread = [4], threadsPerWarp = [32], warpsPerCTA = [4]}>: each thread owns 4 consecutive floats. That is the same decision tinygrad's UPCAST 4 makes, expressed as a layout instead of a loop transformation. With 128 threads and 1024 elements, each thread handles two chunks of 4.
  • The LLVM IR already contains the vector load as inline PTX assembly (ld.global.v4.b32) emitted by Triton's lowering, not chosen by LLVM.
  • The PTX header says Generated by LLVM NVPTX Back-End and .reqntid 128. Parameter names, .loc line info pointing back into the Python file, and debug sections make it long, but the instructions are the same family as NVRTC's (NVRTC's NVVM is itself built on LLVM).
  • Inductor compiled the kernel twice during autotuning, with 4 and 8 warps; the capture keeps both (pick one in the drop-down). The 4-warp kernel is the one above: LDG.E.128, FADD, STG.E.128. The 8-warp one has XBLOCK 512 and sizePerThread = [2], so each thread moves 2 floats with LDG.E.64 and STG.E.64.

So the three routes differ in who writes the text and which optimizer sees it first, but all of them hand ptxas a short, regular program, and ptxas produces near-identical code. Most of the performance was decided earlier, in the choice of what each thread does (chapter 6), not in this last mile.

Inductor's add is reported at 7.1 µs by torch.profiler, against tinygrad's 22.46 µs (add_ptx/cuda; 21.57 µs in add/default) from CUDA events. The torch number is measured differently and is faster than the L4's DRAM can move 12 MB, so the data was likely resident in the 48 MB L2 cache. Don't read it as a 3× win for Triton's code; the SASS says the kernels are equivalent.

Summary

  • linearize orders the graph by loop depth and op priority while staying topologically valid; gated stores become IF/ENDIF.
  • CUDARenderer is a pattern matcher producing strings: names by op, single-use values inlined, __launch_bounds__ from the local size, vectors as float4, gates as ?: and if.
  • NVRTC compiles with just --gpu-architecture=sm_89 (plus --minimal) to PTX; the driver's ptxas makes SASS at module load. Compiled sources are cached in SQLite, keyed by the full source text.
  • DEV=CUDA:PTX prints PTX directly from uops: unoptimized, readable names, loops kept as branches. ptxas cleans it up: add 22.46 vs 22.53 µs, matmul 684 vs 690 µs. Where 32-bit index wraparound blocks address folding, as in sum_rows, it costs more: 25.54 vs 27.65 µs.
  • In SASS, kernel arguments are constant-bank operands (c[0x0][0x160]…), thread ids come from S2R, vectors are register quads written by LDG.E.128, and address math collapses into LEA/IMAD.WIDE.
  • Triton reaches PTX through MLIR and LLVM's NVPTX backend; the SASS it ends with looks like tinygrad's.
