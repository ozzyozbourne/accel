Chapter 2

UOps and the rewrite engine

tinygrad has one intermediate representation, the UOp, and one way to transform it: pattern-matching graph rewrites. The lazy tensor graph, the scheduler's kernel graph, each kernel's AST and the final list of instructions are all UOp graphs, and every step between them is a graph_rewrite with a list of rules. In this chapter we take a UOp apart, learn to read the pyrender listings used throughout this book, build the pattern matcher up from UPat, and watch real rules turn relu into a MAX and GELU's tanh into one exp2.

One IR for everything

Most compilers have several IRs: a graph of high-level ops, then a loop IR, then something close to machine instructions, each with its own data structures and passes. PyTorch's torch.compile is like this: an FX graph, then Inductor's loop-level IR, then Triton, then Triton's MLIR dialects, then LLVM IR. tinygrad 0.14 has a single node type for all of it. A Tensor is a thin wrapper around one UOp (__slots__ = "uop", "is_param", "grad", ). The scheduler's kernel graph, a kernel's AST and the linearized program are also UOps. A stage of the compiler is just a set of ops that may legally appear in the graph at that point: RESHAPE exists only in the tensor graph, RANGE appears during scheduling, SPECIAL (a thread index) only after codegen picks launch dimensions.

One node type also means one transformation tool, and that tool is the topic of the second half of this chapter. Chapter 1 showed a + b going through about fifty named passes. Each of those passes is a call to graph_rewrite(graph, rules). If you understand UOps and graph_rewrite, every later chapter is "here are the rules this pass uses".

What a UOp is

Here is the whole data part of the class ():

# NOTE: this should be frozen, but frozen is slower
@dataclass(eq=False, slots=True)
class UOp(RandMixin, metaclass=UOpMetaClass):
  op:Ops
  dtype:DType = dtypes.void
  src:tuple[UOp, ...] = tuple()
  arg:Any = None
  tag:Any = None

Five fields:

  • op: what the node does, a member of the Ops enum (ADD, RESHAPE, RANGE, ...).
  • dtype: the result type. It includes the "weak" types weakint/weakfloat for Python numbers that adopt the dtype of whatever they meet, and void for nodes with no value, such as STORE and SINK.
  • src: a tuple of input UOps. These are the graph's edges, and there are no others. A node knows its inputs but not its consumers.
  • arg: op-specific static data. For a CONST it is the value, for a PERMUTE the axis order, for a REDUCE the pair (op, number of axes), for a BUFFER a ParamArg(slot, dtype, device).
  • tag: a free slot passes use to mark nodes temporarily. The first tensor-graph pass, number the uops, tags the realize targets; in listings this shows as .rtag((0,)).

Shapes are not stored. UOp._shape derives a node's shape from its sources and arg when asked (), and even movement-op arguments are UOps: a RESHAPE's target shape is a STACK of CONSTs in src[1], so a symbolic size is no different from a constant one.

Immutable, and hash-consed

UOps are never modified. The comment says the dataclass "should be frozen", and nothing in the compiler assigns to these fields; to change a node you call replace(), which builds a new UOp (and returns self if nothing differs, ). Immutability makes the second property safe: structurally identical UOps are the same Python object. Construction goes through a metaclass that keeps a cache keyed by all five fields ():

class UOpMetaClass(type):
  ucache:dict[tuple, weakref.ReferenceType[UOp]] = {}
  def __call__(cls, op:Ops, dtype:DType|None=None, src:tuple[UOp,...]=tuple(), arg:Any=None, tag:Any=None, ...):
    ...
    if (wret:=UOpMetaClass.ucache.get(key:=(op, dtype, src, arg, tag), None)) is not None and (ret:=wret()) is not None: return ret
    UOpMetaClass.ucache[key] = weakref.ref(created:=super().__call__(*key))

This is hash-consing. The key contains src, a tuple of UOps, and UOps compare by identity (eq=False), so the lookup is cheap: two nodes are equal exactly when they have the same op, dtype, arg and tag and literally the same source objects. Because every source was itself deduplicated when it was built, that local check is enough to deduplicate whole subgraphs, bottom-up, at construction time. The cache holds weak references, and __del__ removes the entry when the last reference dies ().

A small CPU experiment (tinygrad 0.14 in our venv, DEV=CPU) shows it:

a, b, c = Tensor.empty(1024,1024), Tensor.empty(1024,1024), Tensor.empty(1024,1024)
t = (a*b+c).relu()*2.0
((a*b+c).relu()*2.0).uop is t.uop          # True: built again, same object
len(t.uop.sink().toposort())                # 17

Building the same expression a second time allocates nothing new; every constructor call hits the cache. The animation below shows what this does to a graph that repeats a subexpression.

Hash-consing gives the compiler three things. A graph is a DAG by construction, so a value written twice is computed once unless a pass decides otherwise. Equality is is: a rule like "x/x → 1" only has to compare two pointers. And caches can be keyed on graphs. For caches that must survive across processes there is also UOp.key, a SHA-256 over op, dtype, arg and the keys of the sources (). The schedule cache and the compiled-kernel cache use it, which is why an identical kernel AST is only compiled once.

The op set

Ops is a single enum of about 80 members (). Its order matters, since the comment above it says it "controls the order of the toposort". The groups in the source tell you where in the pipeline each op can live:

Note the short list: no EXP, TANH, SUB in practice, or DIV for floats. The front end expresses everything with these.

GroupOp () names these sets so rules can say UPat(GroupOp.ALU). It also records algebraic facts: Commutative, Associative and Idempotent are sets of ops that rewrite rules consult.

How Tensor methods build UOps

Nearly the whole Tensor API lives in mixins under tinygrad/mixin/: elementwise math, movement, reductions, creation. UOp uses the same mixins, so UOp and Tensor both have .reshape, .sum and .relu. The mixins only need three primitives from the class, and Tensor implements each one by applying the UOp version to self.uop and wrapping the result ():

def alu(self, op: Ops, *src: Tensor) -> Tensor: return self._apply_uop(lambda *u: u[0].alu(op, *u[1:]), *src)
def _mop(self, op:Ops, arg) -> Tensor: return self._apply_uop(UOp._mop, op=op, arg=arg)
def _rop(self, op:Ops, axis:tuple[int, ...]) -> Tensor: return self._apply_uop(UOp._rop, op=op, axis=axis)

On the UOp side, alu is one line, UOp(op, src=(self, *src)) (). _mop builds a movement op with its shape arguments as UOps (), and _rop permutes the reduced axes to the front and emits REDUCE with arg=(op, number of reduced axes) (). Nothing is computed. A Tensor method only adds nodes.

Higher-level functions are written in terms of these few ops. a + b goes __add__ → add → _binop, which promotes dtypes and calls lhs.alu(Ops.ADD, rhs) (). Broadcasting adds no node: the two sources of an ADD may have different shapes and _shape works out the result. relu is a comparison and a select, with a note on why it is not maximum ():

def relu(self) -> Self:
  # NOTE: if you write this as self.maximum(0) the gradient is wrong, passing through half when self is 0
  return (self > 0).where(self, 0)

and the tanh form of GELU is a formula over tanh, which is itself 2*sigmoid(2x) - 1, where sigmoid is built on exp2 (, ):

return 0.5 * self * (1 + (math.sqrt(2 / math.pi) * (self + 0.044715 * self ** 3)).tanh())

So the graph a user builds is often bigger and clumsier than the math. That is deliberate: the front end stays simple and correct (the relu gradient, for one), and the rewrite engine cleans up afterwards. We will see both cleanups below.

Reading pyrender

Every IR listing in this book is printed by pyrender (). Its output is runnable Python that rebuilds the graph. Here is the lazy graph of ((a*b + c).relu() * 2.0) exactly as captured on the L4, with the 17 UOps it describes. Hover a line to see which nodes it defines, or a node to see its fields.

The rules for reading it:

  • Which nodes get a line. A node gets its own line cN = ... if it has more than one consumer, or if its op is in always_rendered (PARAM, LOAD, SPECIAL, RANGE, CONTIGUOUS, STACK, BUFFER, COPY, CALL, FUNCTION, WHERE, END), or if it is a source of the SINK, a STORE or a REDUCE (). Everything else is inlined into its single consumer. CONSTs are always inlined. That is why c11 = a*b + c has a name: both the comparison and the WHERE use it.
  • The number in cN is the node's index in the toposort (), so the numbers have gaps where inlined nodes sit. The root is always ast.
  • Syntax. A generic node prints as UOp(Ops.X, dtype, (srcs...), arg). Common ops print as Python operators (*, +, <) or as the method that builds them: .alu(Ops.WHERE, t, f), .exp2(), .reciprocal(), ._rop(Ops.MAX, (0,)) for a reduce, and later UOp.range(1024, 0, AxisType.WEAK), buf.index(i), .store(v), .end(r), .sink(arg=KernelInfo(...)). Helpers shorten common patterns: UOp.new_buffer('CUDA', 1048576, dtypes.float, 1) is a BUFFER with its size CONST.
  • Tags print as .rtag(...). dtypes print in full, which is why UOp.const(2.0, dtypes.weakfloat) is so long. In your head, read it as 2.0.

Read this way, c13 = (0.0 < c11).alu(Ops.WHERE, c11, 0.0) is relu, and c15 = c13 * 2.0 is the final multiply. The front end built exactly what the Python said.

Patterns: UPat

A rewrite rule is a pair: a pattern that describes a shape of subgraph, and a function that receives the matched pieces and returns a replacement, or None to decline. Patterns are UPat objects (). A UPat mirrors a UOp's fields, but each field is a constraint instead of a value: op can be a set of ops, dtype a set of dtypes, src a tuple of sub-patterns, arg a required value. Any field left as None matches anything. Give a pattern a name and the matched UOp is passed to your function under that name.

A few constructors make patterns read like the math they match. UPat.var("x") matches any UOp and binds it to x. UPat.cvar("c") matches any CONST. Python operators on UPats build ALU patterns through the same mixins that build UOps, so UPat.var("x") * 1 is a pattern for "a MUL of anything and the constant 1". Three source forms control ordering ():

  • a tuple means "exactly these sources in this order";
  • a list means "these sources in any order": the UPat stores every permutation. UPat.alu uses a list for ops in GroupOp.Commutative, so x * 1 also matches 1 * x;
  • a single UPat means "any number of sources, each matching it".

Matching is a short recursive function (). It checks op, name binding, dtype, arg, tag and source count, then recurses into sources and returns every consistent assignment of names. Binding the same name twice requires the same object: store.setdefault(self.name, uop) is not uop. So the pattern UPat.var("x") // UPat.var("x") means "a value divided by itself", and thanks to hash-consing "itself" is a pointer comparison.

Here are real rules from symbolic_simple, the most basic algebra in tinygrad ():

symbolic_simple = pm_data_invalid + PatternMatcher([
  # ** self folding **
  (UPat({Ops.ADD, Ops.XOR, Ops.OR}, src=[UPat.var("x"), UPat.const(0)]), lambda x: x),  # x+0 / x^0 / x|0 -> x
  (UPat({Ops.SHL, Ops.SHR}, src=(UPat.var("x"), UPat.const(0))), lambda x: x),          # x<<0 / x>>0 -> x
  (UPat.var("x") * 1, lambda x: x),    # x*1 -> x
  (UPat.var("x") // UPat.var("x"), lambda x: x.const_like(1)), # x//x -> 1
  ...
  # ** constant folding **
  (UPat(GroupOp.Unary, src=(const_folding_pat,), name="a"), fold_const_alu),
  (UPat(GroupOp.Binary-{Ops.THREEFRY}, src=(const_folding_pat,)*2, name="a"), fold_const_alu),

The first rule uses a list, so 0 + x matches too, and the shift rule uses a tuple because 0 << x is not x. Constant folding hands two constants to fold_const_alu, which evaluates the op in Python with exec_alu () and returns a new CONST. Because rules are plain Python functions, a rule can do arbitrary work and can still say no. The max-folding rule in symbolic () matches the shape of relu and checks that the two constants agree before it commits:

# max folding
((UPat.cvar("a") < UPat.var("b")).where(UPat.var("b"), UPat.cvar("c")), lambda a,b,c: UOp.maximum(a,b) if a.val == c.val else None),

Note the two uses of "b": the value compared and the value selected must be the same UOp. (0 < x).where(x, 0) matches; (0 < x).where(y, 0) does not.

PatternMatcher

A PatternMatcher is a list of (pattern, function) pairs with an index (). At construction it files every pattern under each op it can match, in pdict. Rewriting one node then only looks at the patterns for that node's op ():

def rewrite(self, uop:UOp, ctx=None):
  if len(pats:=self.pdict.get(uop.op, [])):
    if (ler:=uop.__dict__.get('_src_ops')) is None: uop.__dict__['_src_ops'] = ler = {u.op for u in uop.src}
    for _,match,early_reject in pats:
      if not early_reject.issubset(ler): continue
      if (ret:=match(uop, ctx)) is not None and ret is not uop: return ret
  return None

Three details matter in practice. First match wins: patterns are tried in list order and the first one that returns a new UOp is used, so rule order is part of a pass's meaning. Early reject: each pattern knows which ops its direct sources must have, and a node whose sources lack them is skipped without running the matcher. And matchers compose with +: symbolic = symbolic_simple + commutative + PatternMatcher([...]) (), and the scheduler pass you will meet next is named after its sum, symbolic+reduce_collapse+debuf, an abbreviation of symbolic+pm_reduce_simplify+pm_const_buffer_folding+pm_remove_bufferize (). By default each pattern is also compiled to specialized Python the first time it is used (UPAT_COMPILE, ); the behavior is the same as the interpreter above, only faster.

A function can also take a ctx argument. graph_rewrite(..., ctx=obj) passes the same object to every rule, which is how rules collect information (the scheduler's realize map, a list of buffers) or read configuration (the renderer, in codegen).

graph_rewrite

PatternMatcher.rewrite handles one node. graph_rewrite applies it to a whole graph ():

def graph_rewrite(sink:UOp, pm:PatternMatcher, ctx=None, bottom_up=False, name=None, bpm=None, walk=False, enter_calls=False) -> UOp:
  rewrite_ctx = RewriteContext(pm if not bottom_up else None, pm if bottom_up else bpm, ctx, enter_calls)
  return rewrite_ctx.walk_rewrite(sink) if walk else rewrite_ctx.unified_rewrite(sink)

The work is in unified_rewrite (), an explicit stack machine. Python recursion would overflow on graphs with tens of thousands of nodes, so the recursion is unrolled into a stack. Each node goes through up to three stages:

  1. Stage 0. If there is a bpm (the matcher passed with bottom_up=True), apply it to the node over and over until it returns nothing (a fixed point; a loop raises "infinite loop in fixed_point_rewrite"). Then push the node's sources.
  2. Stage 1. When all sources have been rewritten, rebuild the node if any source changed. If none changed and there is a pm (the default mode), try the rules on the node now.
  3. Stage 2. If stage 1 produced a new node, by rebuilding or by a rule, that node goes through the whole process itself, and its final result becomes the result of the original node.

Stage 2 is the fixed point. A rule's output is rewritten again, so rules can rely on each other: one rule reassociates (x*2)*3 into x*(2*3), and constant folding then sees 2*3. Rewriting stops only when no rule matches anywhere. The replace dictionary memoizes results, so a shared node is rewritten once no matter how many consumers it has. The names of the two modes are easy to misread, so here is the operational difference:

  • Default (pm): a node's sources are finished before rules are tried on it. Rules see simplified inputs. Symbolic simplification runs this way.
  • bottom_up=True (bpm): rules are tried on a node before its sources, and again after a rebuild. A rule can raise BottomUpGate to say "don't descend below here". The scheduler uses this mode for passes that must see the original structure before anything below it changes, such as apply rangeify and stage to store.

There is also walk=True, a single pass with no re-traversal of rewritten subtrees (), and enter_calls, which controls whether the rewrite descends into kernel bodies inside a CALL.

Some things to notice. In ((x*1)+0)*(3+4) the default mode reaches x*7; the real symbolic matcher gives the same result on the same expression (a CPU experiment: graph_rewrite((a*1+0)*(3+4), symbolic) renders as (a*7)). In ((x*2)*3)+0, reassociation creates a node, 2*3, that did not exist before, and the fixed point folds it. In the relu preset, the max rule only fires because both copies of y are equal. In the real graph they are one node, c11.

Real rules at work: relu becomes MAX, and back

Passes are named graph_rewrite calls, and the capture harness recorded every one with the graph after it. Here is the scheduler half for fused_chain, opened at symbolic+reduce_collapse+debuf (). That pass runs symbolic over the kernel graph, and line c19 shows the max-folding rule's work (the other green lines were only renumbered): (0.0 < x).alu(Ops.WHERE, x, 0.0) has become UOp(Ops.MAX, dtypes.float, (0.0, x)), and the graph shrank from 25 to 24 UOps. (A CPU experiment that logs which rule returned a value during this pass for the same expression reports exactly one: symbolic.py:261.)

Step back one pass to see the graph before: apply rangeify has already replaced the reshapes with c9.index(c6) loads at index c6 = c3*UOp.const(1024, dtypes.weakint)+c5. That is the subject of Chapter 3. Here we follow the MAX. It survives scheduling and most of codegen, and is then undone. The CUDA renderer's table of ops it can print has no MAX (), and codegen's early decompositions pass adds a rule for exactly that case ():

# MAX can be rewritten as CMPLT + WHERE (max function is annoying on many cstyle backends)
if Ops.MAX not in ops and Ops.CMPLT in ops: pat.append((UPat(Ops.MAX, name="m"), lambda m: (m.src[0] < m.src[1]).where(m.src[1], m.src[0])))

The matcher is built from ren.code_for_op.keys(), so the rule set depends on the target. This is how one engine serves many backends: each renderer's capabilities decide which rules are added. Why fold into MAX at all, if it is unfolded later? In between, symbolic rules use MAX's value bounds and algebra (GroupOp.Idempotent, Associative) instead of reasoning about a select. The final CUDA C has (0.0f<alu1)?alu1:0.0f, but NVRTC turns the select back into a max: the PTX already has max.f32 against 0f00000000, which ptxas emits as one FMNMX (float min/max) per element, next to the FFMA that fused a*b+c.

The comparison is instructive.

  
    
    
  • Granularity. FX nodes are ATen operators: aten.mul.Tensor, aten.relu.default. There
      are about two thousand of them, and most have a dedicated eager kernel (many are composites of others). tinygrad's graph uses a few dozen primitive ops,
      so relu is not an op at all but a CMPLT and a WHERE. Inductor still has to
      decompose and lower ATen ops; tinygrad's front end already did.
    • 
    
  • Representation. An FX graph is a mutable, ordered list of Nodes with explicit users, which passes edit
      in place. A UOp graph is immutable and hash-consed, and a pass returns a new graph.
    • 
    
  • One IR versus several. Inductor lowers FX to its own loop-level IR: the pre-fusion tab shows
      ops.load, ops.mul, ops.relu inside a loop_body over
      {p0: 1024, p1: 1024}. Then it produces Triton source and hands it to Triton's compiler. tinygrad does the
      analogous step, loops over index variables, by rewriting the same UOp graph (Chapter 3).
    • 
    
  • Rewrite rules. Inductor also has a pattern matcher, torch/_inductor/pattern_matcher.py, which it uses
      in its FX passes (for instance post-grad passes that replace subgraphs with fused or cheaper equivalents). The idea is the
      same as PatternMatcher: patterns over graph nodes plus a replacement. The difference is reach. In Inductor,
      pattern rewriting is one tool among several, while in tinygrad every pass from the tensor graph to the final instruction
      list is a graph_rewrite.

Summary

  
    
    
  • A UOp is (op, dtype, src, arg, tag), immutable and hash-consed through
      UOpMetaClass.ucache. Equal subgraphs are one object, graphs are DAGs by construction, and equality is is.
    • 
    
  • Tensor methods only build UOps, through three primitives (alu, _mop, _rop) shared
      with UOp via mixins. The front end writes naive graphs on purpose.
    • 
    
  • pyrender names a node when it has several consumers or is always rendered; the rest is inlined.
    • 
    
  • A UPat is a pattern with named holes, a PatternMatcher tries patterns indexed by op, first
      match wins, and graph_rewrite applies one to a whole graph until nothing changes, either sources-first or
      node-first (bottom_up=True).
    • 
    
  • The real rules are small and generic. relu becomes MAX through symbolic.py:261 and is turned back
      into a select because the CUDA renderer has no MAX; GELU's tanh collapses into one exp2
