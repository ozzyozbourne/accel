Chapter 11 · Appendix

The debug toolbox

Every artifact in this book can be reproduced with switches that ship with tinygrad, NVIDIA's command-line tools and PyTorch. This appendix lists them stage by stage, says exactly what each one prints and where in the source that happens, shows how to render CUDA for an L4 on a laptop with no GPU, walks through the harness that captured the book, and ends with a cheat sheet for reading PTX and SASS, including an interactive decoder for the control bits hidden in every SASS instruction.

DEBUG, level by level

DEBUG is a ContextVar (), so you can set it in the environment for a whole run or with with Context(DEBUG=4): for one block. The capture harness used the second form to time kernels. Each level prints everything the lower levels print, plus more. The official table in docs/env_vars.md is a good summary but not exact for this commit, so here is what the source actually does at each threshold:

Reading a DEBUG=2 line

The DEBUG=2 line is the one you will look at most. Here is a real one from the L4: the first call of the TinyJit demo in chapter 10 (capture jit/default). Hover over or tap each field:

The line is printed by . The two bandwidth numbers come from the kernel's Estimates: mem counts each buffer once, the unique bytes the kernel must move, and lds counts every load and store the code issues. A large gap between them, like 2 vs 667 GB/s here, means the kernel rereads the same data many times. For a matmul-like kernel that is expected, and caches and registers absorb most of the rereads. The header turns green the first time a kernel runs and magenta when the JIT runs it (). Set NO_COLOR=1 to drop the ANSI codes when you pipe the output.

Watching the passes: VIZ, viz.cli, TRACK_MATCH_STATS

VIZ=1 () turns on TRACK_MATCH_STATS=2 (). Every graph_rewrite then records its input, every pattern that matched, and the output. VIZ also turns on PROFILE and sets PARALLEL=0, so compiling happens in-process where the recorder can see it (). At exit tinygrad writes /tmp/rewrites.pkl.<user>, and if stdout is a terminal it execs the web viewer (). The viewer shows each pass as a graph you can click through, with the rule that fired highlighted.

VIZ=-1 records but does not open the viewer. At exit, once both the rewrite trace and the profile are saved, launch_viz prints saved viz files, view using: python -m tinygrad.viz.cli (; VIZ=1 prints the same line when stdout is not a terminal). The CLI () is very handy over SSH. For the NULL-device a + b:

Smaller lenses

  • DEBUG_RANGEIFY=1 () prints the rangeify table shown in chapter 1: consumers, op, shape, ending ranges, and input → output ranges, with *** on nodes that get realized. Use it with NO_COLOR=1.
  • DEBUG_LINEARIZE=1 () prints the linearizer's priority key for each uop, (run_count, priority, extra). That explains why PARAMs come first (−20), loads early and stores late.
  • print_uops () prints a linear program. pyrender turns any graph into Python that rebuilds it. That is the format of every IR dump in this book.
  • Tensor.schedule_linear() () returns the list of kernel CALLs without running them. call.src[0] is each kernel's AST.
  • BEAM_DEBUG=1 prints the AST under search and each failed candidate ().

These are not debugging aids. They change what gets generated, and each one is part of the codegen cache key (to_program_config), so flipping one recompiles. The book's variants use five of them:

Rendering CUDA for an L4 without a GPU

Most of the codegen in this book can be studied on any machine. tinygrad has a NULL device that accepts any renderer class () and "runs" kernels by doing nothing. Two obstacles remain. CUDARenderer loads libnvrtc in its constructor (), so DEV=NULL:CUDA:sm_89 fails with failed to load library nvrtc. NVCCRenderer is a subclass that renders identical C and only calls nvcc when it compiles, so we pick it and replace its compiler with the base Compiler, whose compile just returns the source bytes ():

# DEV=NULL:NVCC:sm_89 DEBUG=4 PARALLEL=0 python null_cuda.py
from tinygrad import Tensor, Device
from tinygrad.device import Compiler
Device[Device.DEFAULT].renderer.compiler = Compiler()   # "binary" = source bytes; nvcc is never called
a, b = Tensor.empty(1024, 1024), Tensor.empty(1024, 1024)
(a + b).realize()

We ran exactly this while writing the book. It printed E_8192_32_4 opts: (Opt(op=OptOps.UPCAST, axis=0, arg=4), Opt(op=OptOps.LOCAL, axis=0, arg=32)), and the CUDA source matches the L4 capture byte for byte except for a trailing newline. Codegen depends only on the renderer and the arch string, not on the GPU being present. Use Tensor.empty so nothing is copied in; the NULL device cannot copy out (NULL_ALLOW_COPYOUT). All the env vars above work, so NOOPT, TC, BEAM (fake timings, so not meaningful), VIZ and DEBUG_RANGEIFY can all be explored this way. The reported time is a fake 1 ms.

To skip the runtime entirely, call codegen on scheduled ASTs:

from tinygrad import Tensor
from tinygrad.helpers import Target
from tinygrad.uop.ops import Ops
from tinygrad.device import Compiler
from tinygrad.renderer.cstyle import NVCCRenderer
from tinygrad.codegen import to_program

ren = NVCCRenderer(Target("CUDA", "", "sm_89")); ren.compiler = Compiler()
t = Tensor.empty(1024, 1024) + Tensor.empty(1024, 1024)
for call in t.schedule_linear().src:
  if call.src[0].op is Ops.SINK:
    prg = to_program(call.src[0], ren)            # PROGRAM.src = (SINK, LINEAR, SOURCE, BINARY)
    print(prg.arg.global_size, prg.arg.local_size, prg.src[2].arg)

DEV=NULL:PTX:sm_89 fails similarly because the PTX renderer wants nvJitLink. The same compiler swap should work, but we did not test it.

Below tinygrad: ptxas, cuobjdump, nvdisasm

On the CUDA device tinygrad never sees SASS: it hands PTX to cuModuleLoadData, and the driver compiles it. To look at the machine code yourself, get the PTX (DEBUG=5 prints it; the harness grabs the BINARY uop) and run NVIDIA's offline tools. This is what capture.py's sass_of did for every kernel in the book:

$ ptxas -arch=sm_89 -v -o k.cubin k.ptx
ptxas info    : 0 bytes gmem
ptxas info    : Compiling entry function 'E_8192_32_4' for 'sm_89'
ptxas info    : Function properties for E_8192_32_4
    0 bytes stack frame, 0 bytes spill stores, 0 bytes spill loads

$ cuobjdump -sass k.cubin          # needs nvdisasm on PATH as well
$ nvdisasm -c k.cubin              # the raw disassembler; -g adds line info if the cubin has it
$ cuobjdump -res-usage k.cubin     # REG / SHARED / CONSTANT[0] per function (the PyTorch harness used this)

How to read ptxas -v:

  • registers: per thread. Together with the block size this caps occupancy. The L4 has 65,536 registers per SM.
  • barriers: named barriers used. sum_rows/default reports used 1 barriers, 64 bytes smem for its __syncthreads and its 16-float shared buffer.
  • stack frame, spill stores, spill loads: anything nonzero means local memory. sin/default reports a 32 bytes stack frame, from the slow path of CUDA's sinf argument reduction (its SASS has STL/LDL; see chapter 8).
  • cmem[0]: constant bank 0, which holds the kernel parameters starting at 0x160 on this architecture.

tinygrad can also do this itself: at DEBUG=7, cuda_disassemble writes the binary to a temp file, runs ptxas on it when it is PTX, and prints nvdisasm output (). If either tool is missing it prints Failed to generate SASS … Make sure your PATH contains ptxas/nvdisasm. One caution: the SASS from your local ptxas is not guaranteed to match what the driver's JIT produced, because the two can be different versions. The book uses the standalone tool consistently for both frameworks.

How this book captured everything

harness/capture.py runs one example per process, so env vars and caches start fresh, and records every stage. Its central trick is a hook on graph_rewrite. Each tinygrad module imports graph_rewrite by name (from tinygrad.uop.ops import graph_rewrite), so patching tinygrad.uop.ops.graph_rewrite alone would not be seen by the callers. The harness therefore replaces the name in each module that uses it, and tags each module with a stage:

STAGE_OF_MODULE = {"tinygrad.tensor": "tensor", "tinygrad.schedule": "schedule", "tinygrad.schedule.rangeify": "schedule",
                   "tinygrad.schedule.indexing": "schedule", "tinygrad.schedule.multi": "schedule",
                   "tinygrad.codegen": "codegen", "tinygrad.codegen.opt.postrange": "codegen", "tinygrad.engine.realize": "program"}

def make_hook(module):
  stage = STAGE_OF_MODULE[module]
  def hooked(sink, pm, ctx=None, bottom_up=False, name=None, **kw):
    out = orig(sink, pm, ctx=ctx, bottom_up=bottom_up, name=name, **kw)   # run the real pass
    if stage == "codegen" and name == "multi_pm":       # first pass of full_rewrite_to_sink: a new kernel starts
      kernels.append({"ast": clip(render(sink))})
    rec = {"stage": stage, "name": name, "nodes": len(out.toposort()), "changed": out is not sink, ...}
    if name == "linearize/render" and out.op is Ops.PROGRAM: grab_program(out)   # uops, source, PTX
    elif out is not sink: rec["ir"] = clip(pyrender(out))                       # IR after the pass
    passes.append(rec)
    return out
  return hooked

for module in STAGE_OF_MODULE:
  m = importlib.import_module(module)
  if hasattr(m, "graph_rewrite"): m.graph_rewrite = make_hook(module)

Some details that make it work:

  • Identity tells you whether a pass changed anything. UOps are hash-consed: building the same node twice returns the same object. So if out is sink after a pass, the pass did nothing, and the harness stores no IR for it. That is the "faded bar" in every pass stepper.
  • Kernels are delimited by multi_pm, the first named pass of full_rewrite_to_sink (). Its input is the kernel AST.
  • linearize/render returns a PROGRAM whose sources are (SINK, LINEAR, SOURCE, BINARY) (). grab_program reads the name, launch sizes and applied opts from them, prints the LINEAR as the uop table, and keeps the source and the binary. On CUDA the binary is NVRTC's PTX.
  • PARALLEL=0 keeps compilation in the process. Otherwise worker processes would run codegen where the hook does not reach.
  • Timing reruns the same graph five times under Context(DEBUG=2), captures stdout, parses the *** lines, and keeps each kernel's minimum.
  • BEAM compiles many candidates through the same passes. The harness keeps only the last compile of each kernel name, which is the winner, and drops the rest.
  • SASS: sass_of runs ptxas -arch=sm_89 -v and cuobjdump -sass on the PTX, as above. build_data.py later strips the hex encodings, counts opcodes for the instruction-mix charts, and extracts register counts.
  • Checking: the output is compared with a numpy reference, and every capture in the book matched.

The hook sees only passes that go through graph_rewrite. apply_opts' shift_to substitutions and memory_coalescing use substitute (), so they appear in VIZ but not in our steppers. Their effects show up in the next named pass (flatten range and add images).

Cheat sheet: reading SASS

SASS is the real ISA. For sm_89 each instruction is 16 bytes: an opcode and operands in the low 64 bits, and in the high bits a control code: stall counts and dependency-barrier bits that the compiler, not the hardware, chooses to schedule instructions. NVIDIA does not document the encoding. The field layout below is the one reverse engineered in public research on Volta and later GPUs. Our decoding of the capture is self-consistent: the barrier that each LDG sets is exactly the one that its first consumer waits on.

PatternMeaning
R0…R254, RZ32-bit per-thread registers; RZ reads as zero. R2.64 is the pair R2:R3 used as a 64-bit address.
UR4, URZ, ULDCuniform registers: one value for the whole warp, held once. ULDC.64 UR4, c[0x0][0x118] loads a 64-bit value from constant memory into UR4:UR5. Here it is the global memory descriptor that every .E access uses implicitly.
P0…P6, PT, !P0predicate registers; PT is true. @P0 EXIT runs only where P0 is set; @!P0 where it is clear.
c[0x0][0x160]constant bank 0, byte offset 0x160: the first kernel parameter on this architecture. Parameters are 8-byte pointers in order. c[0x0][0x28] is the initial stack pointer.
S2R Rx, SR_CTAID.X / SR_TID.Xread a special register: blockIdx.x / threadIdx.x. Variable latency, so it sets a scoreboard barrier.
LDG / STG .E .128 .64 .U16global load/store; .E = 64-bit (extended) address; the size suffix is the access width in bits (no suffix = 32). .CONSTANT = read-only path.
LDS / STS, LDL / STLshared memory / thread-local (stack or spill) memory.
FADD FMUL FFMA FSETP FMNMXfp32 add, multiply, fused multiply-add, compare-to-predicate, min/max.
IMAD IADD3 LEA SHF LOP3.LUTinteger multiply-add (also used as a plain move, IMAD.MOV), 3-input add, shift-and-add, funnel shift, any 3-input bitwise function given by an 8-bit truth table (0xc0 = a AND b).
IMAD.WIDE32×32+64 → 64: the classic base + index*4 address computation.
MUFU.EX2 .RCP .SIN …the multi-function unit: approximate transcendentals (chapter 8).
HMMA.16816.F32tensor-core matrix multiply-accumulate, m16n8k16, fp32 accumulate (chapter 7). matmul_fp16/default has 16 of them in its inner loop.
BAR.SYNC.DEFER_BLOCKING__syncthreads().
BSSY / BSYNCmark divergence and reconvergence points around branches.
.reuseoperand reuse cache hint: the same register is read again by the next instruction, so it need not go through the register file again.
EXIT; BRA self; NOPend of thread, then a branch-to-self and NOPs that pad the code to an alignment boundary.

Click any instruction of E_8192_32_4 to decode it, including the control code that build_data.py strips from the displayed listings. The raw 128-bit words come from the capture's cuobjdump output. Instructions that depend on the selected one through a scoreboard barrier are highlighted.

Read the control codes top to bottom and the schedule appears. The two S2Rs set barrier 0 and LEA waits on it (wait mask bit 0). Both LDG.E.128 set barrier 2, and the first FADD waits on barrier 2. Both loads were issued back to back before it, so their memory latency overlaps. The IMAD.WIDE for the output address sits between the loads and the adds, where it is free. Fixed-latency ALU instructions use the stall count instead of barriers: SHF stalls 5 cycles before the dependent IMAD.WIDE may issue.

Where to go next. Every chapter's widgets are built from the same capture files. If you want to check something in the book, the fastest loop is: run your expression with DEV=NULL:NVCC:sm_89 DEBUG=4 or VIZ=-1 on any machine, and when you need real numbers, run harness/capture.py on a GPU.
