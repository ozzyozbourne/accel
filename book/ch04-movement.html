Chapter 4

Movement ops become index math

Transposes, broadcasts, slices and pads never move data in tinygrad. They are nodes in the lazy graph until rangeify turns each one into a small change to an integer index expression. This chapter follows four examples from the graph to the index math, to the CUDA C, to the addresses a warp sends to memory. It ends with why the transpose kernel's loads are scalar and its stores are float4, what a padding mask looks like as predicated SASS, and how PyTorch eager and Triton do the same jobs.

No views, only UOps

Older tinygrad tracked strided views with a ShapeTracker. Version 0.14 has none: searching the tree for ShapeTracker or class View finds nothing. A movement op is an ordinary UOp in the tensor graph, and the op enum says so directly: “the core 6 movement ops! these only exist in the tensor graph” . The group is {RESHAPE, EXPAND, PERMUTE, PAD, SHRINK, FLIP} . UOp._mop builds each one with its shape arguments as extra sources (a STACK of constants), while PERMUTE and FLIP keep a plain Python tuple in arg .

RESHAPEnew shape, same element order
PERMUTEreorder axes (1,0)
EXPANDadd new leading axes
PADadd zeros: begins, ends
SHRINKa window: begins, sizes
FLIPreverse axes

Here is the lazy graph for the hardest example in the chapter, a[::2, 1::3].pad(((1,1),(2,2))).contiguous() on a 1000×1000 input. The buffer itself is flat, so the graph starts with a RESHAPE to (1000, 1000). Python's strided slice is not a primitive. _apply_view_ops builds it from a SHRINK to the window [0:1000, 1:1000], a RESHAPE to (500, 2, 333, 3) that gives each step its own axis, and a SHRINK to (500, 1, 333, 1) that keeps index 0 of every step. A RESHAPE to (500, 333) follows, then the PAD . Read the nested line from the inside out:

That is six movement ops and one buffer, and none of them has touched memory yet. When .contiguous() forces the result to exist, the scheduler has to produce one kernel that writes 502 × 337 = 169,174 floats, and each float needs to know where it comes from.

Rangeify: ranges flow backward through the graph

Rangeify (run_rangeify in schedule/indexing.py) starts at the stores. Every value that is materialized gets fresh loop variables, RANGE UOps, one per axis of its shape. Those ranges then travel backward from consumer to producer. A movement op does not change the data. It changes the tuple of index expressions on its way to its source. The whole definition fits in a dozen lines :

# this is the definition of the movement ops
def apply_movement_op(op:Ops, in_shape:tuple[sint,...], arg:tuple, rngs:tuple[UOp, ...]) -> tuple[UOp, ...]:
  match op:
    case Ops.SHRINK:  rngs = tuple(a if off == 0 else a+off for a,(off,_) in zip(rngs, arg))
    case Ops.PERMUTE: rngs = tuple(rngs[p] for p in argsort(arg))
    case Ops.FLIP:    rngs = tuple(((s-1)-a) if f else a for a,s,f in zip(rngs, in_shape, arg))
    case Ops.EXPAND:  rngs = rngs[len(arg):]
    case Ops.PAD:
      rngs = tuple(r if (sz == sh and off == 0) else (r-off).valid(graph_rewrite((r >= off) & (r < (sh+off)),
        symbolic+pm_simplify_valid, name="pad")) for r,sh,(off,sz) in zip(rngs, in_shape, arg))
    case Ops.RESHAPE:
      ...  # _apply_reshape: flatten the output ranges with strides, then % and // by the input shape, then simplify

Read each case as “if my output is indexed by rngs, my input is indexed by …”:

  • SHRINK adds the window's start offset to the index.
  • PERMUTE reorders the index tuple (with the inverse permutation, because the ranges go backward).
  • FLIP mirrors an index: s-1-i.
  • EXPAND drops the leading ranges.
  • PAD subtracts the begin offset and attaches a validity condition. x.valid(cond) builds WHERE(cond, x, Invalid), an index that can be “nowhere”.
  • RESHAPE is the only case that does real arithmetic. _apply_reshape linearizes the output indices into one flat offset, then splits it with % and // by the input shape . The comment there explains why this suffices: “this simplify is doing a lot of heavy lifting. this is the replacement for the reshape view merging code” . The symbolic engine from Chapter 2 cancels the (a*1000+b)//1000 patterns that chains of reshapes produce.

The named pass apply rangeify applies the result. Its matcher pm_apply_rangeify puts .index(...) on every buffer, turns PAD into valid.where(x, 0), and finally deletes the movement ops. After this pass the graph contains no movement op. It has loads and stores at integer addresses built from RANGEs.

Transpose: one kernel, two access patterns

a.T.contiguous() is a PERMUTE on a RESHAPE of a 1M-element buffer. In the pass stepper below, the step after apply rangeify shows the whole effect of the transpose in two index expressions. The store goes to c3*1024+c5 (row-major order of the output) and the load comes from c5*1024+c3, with the same two ranges in swapped roles. Step forward to watch the codegen passes turn these ranges into thread indices.

Next, the optimizer picks opts (Chapter 6 covers them in depth). For this kernel the hand-coded heuristic applied UPCAST(1,4), LOCAL(0,8), LOCAL(1,16). The upcast comes from a fallback rule: when no axis has a broadcast (stride-0) buffer to exploit, upcast the last axis by 4 . The last axis is the output's column, which is contiguous in the output and strided by 1024 in the input. So the output side gets the vector and the input side does not:

Read it with the thread layout in mind. The block is 8 × 16 = 128 threads (__launch_bounds__(128)), and threadIdx.x (lidx0, 8 values) varies fastest within a warp, so a warp is 8 lidx0 × 4 lidx1. The heuristic picked those local sizes: from the last axis down, take the largest of 16, 8, 4, 3, 2 that divides the axis and keeps the block at 128 threads or fewer (32 is also allowed, but only for axis 0) . Globals are assigned in reverse , which is why the axis of size 128 became blockIdx.y.

  • Loads: alu0 = lidx0 + (gidx1<<3) + …, so the 8 lidx0 lanes read 8 consecutive floats, 32 bytes. Each thread then loads 3 more scalars at +1024, +2048, +3072, one input row apart. In SASS these are four LDG.E at offsets +0x1000, +0x2000, +0x3000 bytes.
  • Store: the four values become one make_float4 and one STG.E.128, because the four upcast lanes are consecutive in the output. memory_coalescing (in add images, look for the SHRINK(..., 4) store) folded them into one vector access . It allows lengths 4 and 2 when the renderer supports float4, provided the offset divides the length .

The input side can't be vectorized. The four values a thread needs are 4 KB apart, and no single instruction loads four floats from four rows. A transpose always pays somewhere. What matters is whether the warp as a whole wastes bandwidth, and that brings us to coalescing.

Coalescing: what a warp asks memory for

A GPU never loads one float. When a warp executes a load, the 32 lanes' addresses are merged, and the memory system moves whole 32-byte sectors (four of them make a 128-byte cache line). An access is coalesced when the lanes' bytes fill the sectors they touch. If 32 lanes each want 4 bytes from 32 different sectors, the hardware moves 1024 bytes to deliver 128, which is 12.5% efficiency. Pick a pattern below and issue it. Every pattern except the two that are marked uses the address formula of a captured kernel.

Now the transpose kernel makes sense. Its loads are scalar, but each group of 8 lanes reads a full, aligned 32-byte sector from one row, so every byte fetched is used. The float4 stores write 64 consecutive bytes per output row. Both sides are 100% sector-efficient. Compare transpose (eager, one thread per output), where neighbouring lanes are a full row apart and 7 of every 8 bytes fetched are thrown away (unless a cache keeps the sector until a neighbouring thread wants it).

The measured times agree. The transpose kernel ran in 23.55 µs on the L4, close to the 21.57 µs of the plain 1024×1024 add kernel E_8192_32_4 from Chapter 1, which moves 50% more bytes (12.6 MB vs 8.4 MB). The tile shape (8 rows × 16·4 columns per block) is what keeps the transpose this cheap.

How to read the times in this chapter. tinygrad times a kernel with a pair of CUDA events around each launch on the default stream , so its numbers include launch overhead. Even a kernel that does almost nothing measures about 14 µs (Chapter 5's 16-thread r_16_16 took 14.34 µs). PyTorch's numbers come from torch.profiler, which reports kernel execution time only. All inputs here are 4–12 MB, so between the five timed runs they stay in the L4's 48 MB L2 cache. Compare kernels measured the same way, and treat cross-framework gaps for tiny kernels with suspicion.

Broadcast: a range replaced by zero

a + b.reshape(1, 1024) adds a row vector to every row. The captured tensor graph has no EXPAND: an ADD whose sources have shapes (1024, 1024) and (1, 1024). Broadcasting lives in the shape computation, and rangeify handles it in broadcast_rngs, which replaces the range of a broadcast axis with the constant 0 for that source . After simplification the index of b uses only the column range:

The optimizer treats broadcast axes specially. The upcast loop prefers axes along which some buffer has stride 0, because upcasting such an axis lets one loaded value serve several outputs. The kernel E_8_64_32_4_4_4 upcasts both axes by 4, so each thread computes a 4 × 4 tile. In the source, val4 (four floats of b) is loaded once and added to four rows:

The register reuse is good, but the local axes cost something. The heuristic “prioritize[s] making expand axes local” . The expand axis here is the row axis, and it received the 32-wide threadIdx.x. Lanes of a warp are therefore four rows (16 KB) apart. Select broadcast_add: float4 load of a in the coalescing widget: each LDG.E.128 touches 32 sectors and uses half of each. The kernel took 32.77 µs, slower than the plain add (21.57 µs) even though it reads 4 MB less. The heuristic is a heuristic. Chapter 6 shows how BEAM search finds better choices by timing them.

Slice and pad: an index that can be nowhere

Back to the slice-and-pad example. After apply rangeify, the six movement ops have become one affine expression and one condition:

Take it apart (c3 is the output row, 0…501; c6 the output column, 0…336):

  • c15 = (c3 ≥ 1) & (c3 < 501) and c22 = (c6 ≥ 2) & (c6 < 335) are the PAD's validity conditions, written as (c3<1) != True because the symbolic engine normalizes comparisons to <.
  • c3*2000 + c6*3 - 2005 is the slice. Output row c3 is slice row c3-1, which is input row 2(c3-1). Output column c6 is input column 1 + 3(c6-2). Multiply out 2000(c3-1) + 3(c6-2) + 1 and you get exactly the captured constant -2005.
  • c35 = valid.where(index, Invalid) is the gated index, and c38 = valid.where(load, 0.0) is the padded value .

The valid condition has to become a branch-free guard on the load. In codegen, the pass move gates from index rewrites INDEX(buf, gate.where(idx, Invalid)).load() into INDEX(buf, idx).load(0, gate), a load with an alternative value and a gate source . The renderer prints a gated load as a C ternary:

Notice (0<(gidx1+lidx0)). The output row is 2*gidx1 + lidx0, and the simplifier replaced “row ≥ 1” with an equivalent condition: for non-negative integers, 2g + l ≥ 1 exactly when g + l ≥ 1. Switch to the SASS tab to see how the hardware evaluates the guard without a branch:

        /*0060*/                   MOV R7, RZ ;                              // the "else 0.0f" value, preloaded
        /*0080*/                   IADD3 R0, R9, R4, RZ ;                    // lidx0 + gidx1
        /*0090*/                   IADD3 R2, R5, -0x2, RZ ;                  // gidx0 - 2
        /*00a0*/                   ISETP.GE.AND P0, PT, R0.reuse, 0x1, PT ;  // lidx0+gidx1 >= 1
        /*00b0*/                   IMAD.IADD R0, R0, 0x1, R4 ;               // lidx0 + 2*gidx1  (the output row)
        /*00c0*/                   ISETP.GT.U32.OR P0, PT, R2, 0x14c, !P0 ;  // (unsigned)(gidx0-2) > 332  ==  gidx0<2 || gidx0>334
        /*00d0*/                   ISETP.GT.OR P0, PT, R0, 0x1f4, P0 ;       // 2*gidx1+lidx0 > 500
        /*00e0*/              @!P0 IMAD R0, R4, 0x2, R9 ;                    // address math only when valid
        /*0120*/              @!P0 LDG.E R7, [R2.64] ;                       // predicated load
        /*0160*/                   STG.E [R4.64], R7 ;                       // unconditional store

This is an excerpt of the captured SASS: a few address-computation lines and the encoding words are left out, and the comments are added. ptxas computes one predicate P0 = “invalid” and guards the address math and the LDG.E with @!P0. The register R7 already holds 0, so invalid lanes store zero without any branch. One more trick: the two-sided test 1 < gidx0 < 335 became a single unsigned compare, because gidx0 - 2 wraps to a huge unsigned number when gidx0 < 2.

The kernel is correct, but 67.58 µs is slow for 1.35 MB of traffic. The kernel name E_251_337_2 shows the reason: the only opt is LOCAL(0,2), so each block has 2 threads. The output is 502 × 337, and 337 is prime. Neither the 4-way upcast fallback nor any local size from the list divides it, so the column axis got no opt at all. The row axis 502 = 2 × 251 only admits 2. The grid has 84,587 two-thread blocks, and each block occupies a whole warp slot with 2 live lanes (see pad_slice in the coalescing widget). An Ada SM keeps at most 24 blocks resident, so the L4's 58 SMs have fewer than 3,000 threads in flight instead of tens of thousands. Triton sidesteps the problem with masked tiles, as the next sections show.

permute4d: the axis that stays put

a.permute(0,2,1,3).contiguous() on a 32⁴ tensor swaps the middle two axes and leaves the last axis alone. In the captured expressions the last range c5 has stride 1 on both sides:

Because a run of 32 consecutive floats stays consecutive, the upcast by 4 on the last axis vectorizes both sides. The whole kernel body is one float4 load and one float4 store. In SASS that is one LDG.E.128 and one STG.E.128, and the kernel ran in 22.53 µs, the same as a copy:

That is the general lesson about permutes. The cost depends on what happens to the innermost axis. If it stays innermost, a permute is a copy with unusual address math. If it moves, as in a 2-D transpose, someone has to turn rows into columns.

PyTorch: strided iterators and layout conversion

Eager. PyTorch eager has no lazy graph. a.t() returns a view (same storage, strides (1, 1024)), and .contiguous() launches a copy kernel. The captured kernel is elementwise_kernel<128, 2, … direct_copy_kernel_cuda …>, the generic, non-vectorized TensorIterator loop: 128 threads per block and 2 elements per thread. TensorIterator computes each element's input offset from the strides. Output is linear in the thread index, so a warp's stores are contiguous and its loads stride by a full row (the eager pattern in the coalescing widget). It took 26.78 µs. Eager add uses vectorized_elementwise_kernel<4, …> and took 7.01 µs. The broadcast add also falls back to the non-vectorized elementwise_kernel<128, 2> (7.04 µs) because one operand is not contiguous.

Inductor/Triton. torch.compile generates triton_poi_fused_clone_t_0, a 2-D tiled pointwise kernel (tile_hint=TileHint.SQUARE, 32 × 32 tiles). In its source, the load is tl.load(in_ptr0 + (y0 + 1024*x1)) and the store is tl.store(out_ptr0 + (x1 + 1024*y0)), which is the same index swap rangeify produced.

The TTGIR shows what Triton does with the tile. The load uses layout #blocked1: sizePerThread = [4, 1], order = [0, 1], so each thread holds 4 consecutive elements along y, the input's contiguous axis. The store uses #blocked: sizePerThread = [1, 4], order = [1, 0], 4 consecutive elements along x, the output's contiguous axis. Between them sits ttg.convert_layout, which Triton lowers to a round trip through shared memory (the kernel metadata reports shared: 4096, one 32 × 32 float tile). The SASS has two LDG.E.128, eight STS, a BAR.SYNC, eight LDS, and two STG.E.128. Both global sides are fully vectorized and coalesced (transpose (Triton) in the widget). The transpose happens inside the SM, where scattered access is cheap. tinygrad's hand-coded path never uses shared memory for a pure copy. It settles for sector-efficient scalar loads.

For pad_slice, eager launches two kernels: a FillFunctor that zeroes the output (1.63 µs), then a direct_copy into the interior view (2.88 µs). Inductor fuses them into triton_poi_fused_constant_pad_nd_slice_0 (2.53 µs). Its body has the same affine index as tinygrad's, (-2005) + 3*x0 + 2000*x1, and the same validity mask, passed as the load's mask with other=0.0. The difference is the launch shape. Triton runs 1-D blocks over the flattened output, with a mask on the tail, so the prime 337 doesn't matter.

Keep the timing caveat from earlier in mind when reading this chart. The big ratios (tinygrad 67.58 µs vs Triton 2.53 µs on pad_slice, eager 26.78 µs vs Triton 5.22 µs on the transpose) are real differences in launch shape and access pattern. The ratio between tinygrad's ~22 µs copies and Triton's ~5 µs copies is mostly the different timers.

Summary

  • Movement ops are UOps in the tensor graph. Rangeify pushes RANGE tuples backward through them with apply_movement_op, then deletes them. What is left is integer index arithmetic, simplified symbolically.
  • PERMUTE reorders ranges, SHRINK adds offsets, EXPAND drops leading ranges, broadcasting replaces ranges with 0, RESHAPE is // and % that the simplifier cancels, and PAD wraps the index in WHERE(valid, idx, Invalid).
  • A validity mask becomes a gated load (move gates from index), a C ternary, and in SASS a predicate: @!P0 LDG.E over a register preloaded with 0.
  • Vector width follows contiguity. tinygrad's transpose stores float4 and loads scalars, yet stays sector-efficient. permute4d keeps its inner axis and vectorizes both sides.
  • Coalescing is decided by which index threadIdx.x lands on. The heuristic sometimes chooses badly (broadcast_add), and prime sizes can starve it (pad_slice).
  • PyTorch eager does movement with strided TensorIterator copies. Triton tiles the transpose and swaps layouts through shared memory (convert_layout).
