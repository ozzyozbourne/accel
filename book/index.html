Preface

From Python to SASS

This book follows one line of Python, c = a + b, and twenty other small programs, all the way down: from a tinygrad Tensor, through the lazy UOp graph, the scheduler, about fifty named compiler passes, CUDA C, PTX and finally the SASS machine code that an NVIDIA L4 runs. Next to each step we put what PyTorch does with the same program, both in eager mode and under torch.compile. Every kernel, IR dump, register count and timing in the book was recorded on a real GPU. None of it is retyped by hand.

What this book is

A deep learning framework is a compiler with a Python front end. When you write (a * b + c).relu(), nothing is computed. You are building a description of a computation, and the framework later decides how many GPU kernels to launch, how to split the work across thousands of threads, and which machine instructions each thread runs. Most of the interesting engineering lives in that "later", and most users never see it.

tinygrad is a good framework to learn this from. The whole compiler is a few thousand lines of Python, it has no hidden C++ layer, and every lowering step is a named graph_rewrite pass over a single IR, the UOp. You can print the graph after every pass, and the book does: the pass stepper widgets in each chapter show the IR as it really looked after each of the 50 or so passes that ran for each example, recorded while the example compiled on the L4.

PyTorch is the comparison. Eager PyTorch launches prebuilt ATen kernels, one or more per operator. torch.compile uses a pipeline of several separate compilers: Dynamo, AOTAutograd, Inductor, Triton, LLVM, then NVIDIA's ptxas. Seeing the two designs side by side makes both easier to understand: they solve the same problems (fusion, tiling, vectorization, index math), but they put the solutions in different places.

The book is written for readers who know Python and roughly what a GPU is, and who want to understand how the compiler works, all the way down. Each chapter builds intuition first with an animation or a diagram, then shows the real artifact, then points at the lines of tinygrad source that produced it. The source links go to tinygrad at the exact commit the captures used, for example , where the codegen pass list starts.

Read the tinygrad lane from the top:

  
    
    
  1. Tensor → lazy UOp graph. a + b only builds a node: Tensor is a thin wrapper around one UOp (), and arithmetic adds Ops.ADD over the inputs' buffers.
    2. 
    
  2. Schedule / rangeify. realize() () hands the graph to the scheduler. Rangeify gives every node explicit loop variables (RANGE), turns movement ops such as reshape and permute into index arithmetic, decides what fuses, and cuts the graph into kernels ().
    3. 
    
  3. Kernel AST. Each kernel is a SINK of STOREs over loops: the input to codegen.
    4. 
    
  4. Codegen passes. full_rewrite_to_sink () runs the optimizer, which picks opts such as UPCAST and LOCAL. It then runs the expander (loops become vectors), gpudims (loops become blockIdx/threadIdx), devectorize and memory coalescing (vectors become float4 loads), and decompositions (for example, integer multiplies and divides by powers of two, such as ×128, become shifts).
    5. 
    
  5. Linearize. The graph is toposorted into a flat list of uops ().
    6. 
    
  6. CUDA C → NVRTC → PTX. The CUDA renderer prints C (). NVRTC compiles it to PTX, NVIDIA's virtual ISA.
    7. 
    
  7. PTX → SASS. tinygrad hands the PTX to cuModuleLoadData (), and the driver's built-in ptxas JIT-compiles it to SASS, the real machine code. To be able to show that SASS, the harness ran the same PTX through the standalone ptxas and cuobjdump.
    8. 
    
  8. cuLaunchKernel () starts it: 8192 blocks of 32 threads for a + b.
    9. 
  

  
PyTorch's lane. Dynamo reads the Python bytecode and builds an FX graph. AOTAutograd lowers it to ATen ops (and builds the backward graph, if there is one). Inductor lowers ATen to its own loop-level IR, fuses nodes in its scheduler, and writes Python containing a Triton kernel, triton_poi_fused_add_0. Triton then compiles that kernel through its own MLIR dialects: TTIR, then TTGIR, which attaches a thread layout. From there it goes to LLVM IR, PTX (via LLVM's NVPTX backend) and a cubin (via ptxas). Eager mode skips all of that: a + b dispatches straight to at::native::vectorized_elementwise_kernel<4, CUDAFunctor_add<float>, …>, a template compiled into libtorch_cuda.so when PyTorch was built.


  
How the book was made

  
Everything quoted in the book was captured in one session on a Google Colab instance with an NVIDIA L4 (Ada Lovelace, sm_89, 58 SMs). The software was:

The harness lives in book/harness/:

  
    
    
  • examples.py defines every example: its inputs (from a seeded numpy RNG), the tinygrad expression, a numpy reference and the PyTorch version. Variants are environment settings (NOOPT=1, BEAM=2, TC=0, TRANSCENDENTAL=2, DEV=CUDA:PTX).
    • 
    
  • capture.py runs one tinygrad example in a fresh process. It wraps graph_rewrite in every module that imports it, so it sees every named pass with its output IR. It intercepts the final PROGRAM to keep the uops, source and PTX. It runs ptxas -v and cuobjdump -sass on the PTX, checks the result against numpy, and times the kernels five times with DEBUG=2, keeping the best run. Chapter 11 walks through it.
    • 
    
  • capture_torch.py does the same for PyTorch. It uses torch.profiler for eager kernel names and times, TORCH_COMPILE_DEBUG=1 for Inductor's FX graph, IR and output code, and reads the Triton cache directory for TTIR, TTGIR, LLVM IR, PTX and cubin. SASS comes from cuobjdump.
    • 
    
  • run_all.py runs every example and variant in its own process, and build_data.py turns captures/*.json into the data/*.js files these pages load.
    • 
  

  
To re-run it on your own GPU, put ptxas and cuobjdump on PATH and install tinygrad at the commit above plus PyTorch with CUDA. Then run:

  
# from the book/ directory
python harness/run_all.py captures            # all examples; or: run_all.py captures add softmax
python harness/build_data.py                  # captures/*.json -> data/*.js
# then open index.html in a browser (no server needed)


  
Two caveats about the numbers. First, tinygrad's times come from CUDA events recorded around each launch (), while PyTorch's come from the profiler's per-kernel device times. Event timing includes some launch overhead, so short tinygrad kernels look slower than their PyTorch twins for reasons that have nothing to do with code quality. Second, each benchmark reran the same inputs, and the L4 has 48 MB of L2 cache, so a 12 MB working set like a + b is mostly served from L2, not from DRAM. Chapter 1 works through both effects.


  
The chapters

  

    1. The journey of a + bOne elementwise add followed through every stage, from Python to SASS and the launch, then the same add in PyTorch eager and in Triton.
    2. UOps and the rewrite engineThe single IR tinygrad uses everywhere, and how PatternMatcher plus graph_rewrite make up the whole compiler.
    3. Scheduling and fusionHow realize, rangeify and the bufferize cost model decide what fuses into one kernel and what gets its own buffer.
    4. Movement ops become index mathReshape, permute, expand, pad and shrink never move data. They turn into integer expressions over loop variables.
    5. ReductionsSums, maxes, softmax and layernorm: register accumulators, GROUP reductions in shared memory, barriers, and split reductions.
    6. The optimizer: opts, heuristics, BEAMUPCAST, LOCAL, UNROLL, GROUP; the hand-coded heuristic step by step; and what BEAM search finds for a matmul.
    7. Tensor coresHow an fp16 matmul becomes WMMA uops, inline mma.sync PTX and HMMA.16816.F32 in SASS.
    8. Decompositions: exp, sin, integer mathWhat the backend lacks gets rewritten: hardware MUFU versus tinygrad's polynomial transcendentals, and shift-and-multiply integer division.
    9. Rendering and compiling: CUDA C, PTX, SASSUops to CUDA C, NVRTC to PTX, tinygrad's own PTX renderer, and how ptxas turns either into SASS.
    10. Runtime, TinyJit and autogradLaunching kernels, caching, CUDA graphs, symbolic shapes, and how a backward pass is just more UOps.
    11. Appendix: the debug toolboxEvery switch for looking inside: DEBUG levels, VIZ, rendering CUDA without a GPU, ptxas, cuobjdump, the PyTorch logs, and a SASS cheat sheet.

A few patterns are visible even before chapter 1. Every contiguous elementwise example (add, fused_chain, gelu, exp, sin, int_divmod) becomes the same launch shape, E_8192_32_4. Softmax and layernorm are three kernels in tinygrad and one in torch.compile. The fp32 matmul ranges from 37 ms with NOOPT=1 to 224 µs with BEAM search, against 149 µs for cuBLAS.
