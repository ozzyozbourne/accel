Chapter 5

Reductions

A reduction collapses an axis: every output needs many inputs. That makes it the first operation where threads must cooperate. This chapter follows sum(1), max(0) and a full sum() of 16M floats from the REDUCE UOp to register accumulators, shared memory, __syncthreads() and finally BAR.SYNC, STS and LDS in SASS. Along the way it explains why tinygrad turns one a.sum() into three kernels, what a name like r_32_32_4_1024_4 means, and how PyTorch's reduce kernels compare.

REDUCE in the tensor graph

Every reduction in tinygrad (sum, max, prod, and everything built on them such as mean, softmax and matmul) ends up in UOp._rop . It permutes the reduced axes to the front and emits REDUCE(src, arg=(op, n_reduced_axes)), where op is ADD, MUL or MAX. For a.sum(1) on a 1024×1024 input, the reduced axis is the last one, so the graph gets a PERMUTE (1, 0) in front of the REDUCE:

Chapter 4 showed that a PERMUTE is free. It only reorders ranges. Rangeify gives the REDUCE a fresh AxisType.REDUCE range for the reduced axis and passes the output range (WEAK, an ordinary loop axis) through. The kernel AST that codegen receives is short:

Read it as a loop nest: for every output row c2 (1024 of them), reduce over c7 (1024 of them) the value at c2*1024 + c7, then store at c2. max(0) is the same with MAX and the index transposed, c6*1024 + c2: it reduces down a column. Everything interesting happens in codegen, where this loop nest has to be spread over threads.

The optimizer's choice: GROUPTOP

A reduction kernel has two kinds of parallelism. Output elements are independent, so they can go to different threads freely. The reduced elements of one output can also be split across threads, but then the threads have to combine their partial results, which takes shared memory and a barrier. tinygrad's heuristic (Chapter 6 covers it fully) decides with one rule :

  # are we grouping? (requires local shape support)
  if resolve(prod(k.output_shape[i] for i in k.upcastable_dims) <= (240 if NOLOCALS else 2048), False):
    for axis, sz in itertools.product((0, 1, 2), (16,)):
      try:
        k.apply_opt(Opt(OptOps.GROUPTOP, axis, sz))
        break
      except KernelOptError: pass

  # no more opt if we are grouping
  if k.group_for_reduces: return k

If the kernel has at most 2048 outputs, there aren't enough of them to fill a GPU. It then groups the reduce axis by 16: each output gets a block of 16 threads that share the work. Both sum_rows and max_cols have 1024 outputs, so both get GROUPTOP(0, 16) and nothing else. GROUP and GROUPTOP both create an AxisType.GROUP_REDUCE range . The “TOP” means the 16-way split is taken from the top of the axis (shift_to(..., top=True), ). Thread t therefore owns the contiguous chunk [64t, 64t+64) of the 1024 values, not every 16th value.

Reading the kernel name

The name is built in get_optimized_ast: r if there is a reduce and E otherwise, then one number per axis, in axis-type order, each coloured by its type . The colours are lost in the plain function name, but the captured passes keep the raw string, so the widget below decodes them:

r_1024_16_64 is 1024 blocks (global), 16 threads per block that each own a slice of the reduction (group reduce), and a loop of 64 per thread (reduce). 16 × 64 = 1024, the row length. The order is fixed by axis_to_pos: globals, locals and group-reduces, upcasts, reduces, unrolls .

From REDUCE to accumulators: remove reduces

After the opts, the AST still contains a REDUCE with two ranges: the 64-long REDUCE range and the 16-wide GROUP_REDUCE range. The pass remove reduces rewrites it in two steps.

  1. fix_group_for_reduce splits the REDUCE. It first reduces only over the ordinary REDUCE ranges, giving one partial per thread. It then bufferizes those partials into a STAGE in AddrSpace.LOCAL, indexed by the group range. Finally it reduces again over new REDUCE ranges with the axis number plus 100. That is why the CUDA source has a loop variable called Ridx102: range 2 plus 100.
  2. reduce_ranges_to_acc turns each remaining REDUCE into a register accumulator. It creates a BUFFER in AddrSpace.REG, stores the identity element into it before the loop (identity_element is 0 for ADD, 1 for MUL and the dtype's minimum for MAX, ), and stores acc op value inside the loop.

Then add local buffers makes the LOCAL STAGE a real shared-memory BUFFER. add gpudims turns the GROUP_REDUCE range into lidx0 (group-reduce axes count as local dims, ). Because the global store doesn't use lidx0, it is masked with lidx0 == 0 , so only one thread per block writes. add implicit barriers sees a LOCAL load that depends on a LOCAL store and inserts a BARRIER between them (add_raw_barrier, ). Watching one block reduce

The animation runs this kernel for one block. The thread count, both loop lengths and the highlighted source lines are read from the captured kernel. You can switch to the other GROUPTOP kernels in this chapter. Phase 1 is embarrassingly parallel: 16 threads each sum 64 values in a register. Phase 2 needs cooperation. Every thread publishes its partial in shared memory, everyone waits at the barrier, then one thread reads all 16 slots.

Compare the CUDA C with the SASS (tab above). ptxas made three changes:

  • Full unroll of the first loop. It is 64 iterations with constant bounds, so ptxas issued all 64 loads up front (LDG.E R61, [R2.64], [R2.64+0x4], … +0xfc) followed by a chain of FADDs. That explains the 79 registers in ptxas -v: 64 of them hold loaded values in flight. The instruction mix has 64 LDG and 80 FADD (64 + 16).
  • The redundant second loop disappears. In C every thread runs the Ridx102 loop and only lidx0==0 stores. ptxas proved the work of the other threads is dead and emits @P0 EXIT right after BAR.SYNC.DEFER_BLOCKING 0x0.
  • Vector shared loads. Thread 0 reads the 16 partials as four LDS.128, because buf2 is 16-byte aligned and the indices are constants after unrolling.

Memory access is the weak spot. A thread's 64 values are contiguous, so neighbouring lanes are 256 bytes apart: every load instruction touches 16 sectors for 64 useful bytes (Chapter 4's coalescing widget, sum_rows). The next loads hit the same sectors, so the cache absorbs most of the waste. The kernel took 25.6 µs for 4 MB.

Max: identity −∞ and compare-select

a.max(0) reduces down columns and produces the same name, r_1024_16_64, with the same opts. Two things differ. The accumulator starts at -INFINITY (the identity of MAX is dtypes.float.min). And there is no max in the source. CUDA's renderer doesn't list Ops.MAX, so the pass early decompositions rewrites it as (a < b).where(b, a) , which renders as a C ternary:

In SASS each step is an FSETP.GEU.AND (compare into a predicate) plus an FSEL (select): 78 of each. Only the first step of each loop, against the -INF starting value, became an FMNMX (2 in total). ptxas keeps the other compare/select pairs, probably because the ternary's NaN behaviour is not exactly that of fmaxf. This is also why the kernel needs two instructions per element where the sum needs one, and partly why it took 33.79 µs versus 25.6 µs.

The access pattern also differs: gidx0 + (lidx0<<16) + (Ridx0<<10). A block owns one column, and its 16 threads walk down the column 64 rows apart. Each load gets one useful float out of a 32-byte sector. Neighbouring blocks read the neighbouring floats, so the L2 cache recovers most of it. PyTorch eager instead launched reduce_kernel<128, 4, …MaxNanFunctor…>, whose 4 values per thread run along the contiguous axis.

sum_all: one reduction, three kernels

Now the big one: a.sum() over 4096 × 4096 = 16,777,216 floats into one number. A single kernel with a single output would get one block on one SM. The scheduler prevents that before codegen even starts. In earliest rewrites, every REDUCE passes through split_reduceop :

def split_reduceop(reduce:UOp, x:UOp):
  if prod(reduce.shape) == 0: return None
  if not SPLIT_REDUCEOP or not all_int(x.shape) or (prod(x.shape)//prod(reduce.shape))<getenv("REDUCEOP_SPLIT_THRESHOLD", 32768): return None
  ...
  if not (split_candidates:=[(i,d) for i in range(reduce.arg[1])
                             for d in range(min(256,2**getenv("REDUCEOP_SPLIT_SIZE",22)//prod(reduce.shape)),8-1,-1)
                             if x.shape[i]%d==0 and not is_expanded[i]]): return None
  dim_to_split, divisor = split_candidates[0]
  ...
  # reduce original axes, then split
  return splitted._rop(reduce.arg[0], tuple(range(reduce.arg[1]))).contiguous()._rop(reduce.arg[0], (len(reduce.shape),)).reshape(reduce.shape)

The rule : if the reduction ratio (inputs per output) is at least REDUCEOP_SPLIT_THRESHOLD = 32768, find the largest divisor d from min(256, 2²²/outputs) down to 8 that divides the first reduced axis. Reshape that axis into (d, rest), reduce everything except d, force the result to exist with .contiguous() (a kernel boundary), then reduce the d partials. SPLIT_REDUCEOP defaults to 1 . sum_rows doesn't split: its ratio is 1024.

For sum_all the rule fires twice, because the rewrite is applied again to its own output:

  1. Ratio 16,777,216 / 1. Split axis 0 (4096) by 256: shape (4096, 4096) → (16, 4096, 256), reduce to (256,), contiguous, reduce to ().
  2. The new inner reduce, (16, 4096, 256) → (256,), has ratio 65,536, still ≥ 32768. The largest candidate is now min(256, 2²²/256) = 256, but the first reduced axis is 16, so d = 16: reduce to (256, 16), contiguous, reduce to (256,).

A CPU experiment with the same tinygrad (DEV=CPU DEBUG=3) prints both decisions:

On the L4 capture you can see the result directly in the graph after earliest rewrites: two .contiguous() and three _rop(Ops.ADD, …). After apply rangeify the contiguous results became two global STAGEs with removable=False, the cut points that split kernels later turns into separate kernels. The kernel names and shapes on CPU differ (r_256_4_4_1024_4, …) because codegen targets a different device. The schedule is the same.

Look at what the reshapes do to the index of the first kernel. Its AST reads c6*4096 + c12 + c3*65536 and stores at c3*16 + c6, with c12 the 4096-long reduce. The output index c3*16 + c6 is a row number, so kernel 0 computes the 4096 row sums. Kernel 1 adds groups of 16 consecutive row sums, giving 256 partials, and kernel 2 adds those.

Each kernel then goes through the optimizer on its own, and their sizes lead to different opts:

  • Kernel 0, r_32_32_4_1024_4. 4096 outputs is more than 2048, so no grouping. The upcast loop upcasts the output axis by 4 . The reduce is longer than 32, so it is unrolled by 4 . LOCAL 32 completes it: 32 blocks × 32 threads × 4 rows per thread, and a loop of 1024 × 4. Each thread keeps 4 accumulators (float buf0[4], one per row) and loads one float4 from each row per iteration. In expander, the UNROLL turns the 4 loaded lanes into a horizontal add, acc + v.x + v.y + v.z + v.w (expand_horizontal_reduce, ). ptxas unrolled the loop 4 more times: 16 LDG.E.128 per trip, 76 registers, no shared memory.
  • Kernel 1, r_256_16. 256 outputs, so GROUPTOP 16 takes the whole 16-wide reduce. Each thread loads one value, and there is no first loop at all. Thread 0 sums the 16 shared slots.
  • Kernel 2, r_16_16. One output, GROUPTOP 16: 16 threads each sum 16, then thread 0 sums 16. Its second loop is called Ridx101 (range 1 + 100).

The times expose the weakness of kernel 0. It ran in 471.97 µs. Reading 64 MB in that time is about 142 GB/s, roughly half of what the L4's memory can deliver. The launch has only 32 blocks of 32 threads, 1024 threads on a GPU with 58 SMs, so 26 SMs sit idle and each busy SM has a single warp. Each warp's loads are 64 KB apart per lane and half-used per instruction (sum_all kernel 0 in Chapter 4's widget). The two small kernels add 19.46 µs and 14.34 µs, which is almost entirely launch overhead under tinygrad's event timer.

A note on accuracy

A float32 sum of 16M numbers depends on the order of additions. The capture's check compares against a float64 numpy reference: the maximum absolute error was 0.00423 on a result of magnitude 449.33, well within the example's tolerance. The split helps. A CPU experiment (numpy, same seeded input) replays tinygrad's exact order: 4 lanes added left to right into each row accumulator, then groups of 16, then 16 × 16. It gives an error of 0.00423, matching the GPU. A strictly sequential float32 loop over all 16M values is off by 0.151, about 36 times worse, because by the end each new element is added to a running sum hundreds of times larger and loses low bits. numpy's own pairwise float32 sum gets 0.00087. Multi-level reductions behave like a shallow tree: each partial sums only 4096, 16 or 16 values.

PyTorch: one reduce kernel, or persistent and split Triton kernels

Eager. Every reduction goes through TensorIterator's generic reduce_kernel. For sum(1) and sum() the captured kernel is reduce_kernel<512, 1, ReduceOp<float, …sum_functor…, unsigned int, float, 4, 4>>: 512 threads per block, with 4-wide vectorized loads and 4 accumulators per thread (the trailing 4, 4). For the full sum it reduced 16M floats in 264.26 µs in a single launch. It parallelizes across blocks itself, using a global semaphore so that the last block to finish combines the partials. That is what the Memset (Device) before it initializes. max(0) uses reduce_kernel<128, 4, …MaxNanFunctor…>.

Inductor classifies a reduction as persistent (triton_per_*) when the whole reduced axis fits in one block of registers, or looped (triton_red_*) when it does not. For sum(1), a row of 1024 fits: triton_per_fused_sum_0 loads the whole row as a [XBLOCK, 1024] tile and calls tl.sum(tmp3, 1).

Triton lowers tl.sum to a butterfly of warp shuffles (SHFL.BFLY, 5 of them for 32 lanes) and needs no shared memory at all, since the kernel runs with num_warps = 1. Its loads are LDG.E.EF.128: vectorized, with an evict-first cache hint from eviction_policy='evict_first'. Switch the animation above to butterfly to compare the two patterns: tinygrad funnels 16 partials through one thread, while a butterfly needs log₂ 32 = 5 steps in which all lanes work.

For the full sum Inductor also splits into two stages, with a different choice of split. triton_red_fused_sum_0 uses xnumel = 174 and r0_numel = 96421: 174 partial sums of 96,421 elements each. 174 × 96421 is slightly more than 16,777,216, so the load is masked with tmp0 < 16777216. Inductor chose a number of partials that keeps every SM busy (174 = 3 × 58) instead of a divisor of the shape. triton_per_fused_sum_1 then reduces the 174 partials in one persistent block.

For the small reductions most of the gap is the timing method (see the callout in Chapter 4): tinygrad's event timer adds roughly 14 µs per launch, and these kernels do a few microseconds of work. For sum_all the comparison is meaningful, because the work dominates. tinygrad's 505.77 µs total against eager's 264.26 µs and Triton's 284.67 µs is the cost of 32 blocks with half-used load instructions against launches that fill all 58 SMs.

Summary

  • _rop emits REDUCE(op, n_axes) after permuting the reduced axes to the front. Rangeify gives it REDUCE ranges.
  • Large reductions (ratio ≥ 32768) are split in the tensor graph by split_reduceop, repeatedly. 16M → 4096 → 256 → 1 gives three kernels for sum_all.
  • With at most 2048 outputs the heuristic applies GROUPTOP 16. remove reduces turns the REDUCE into a register accumulator, a shared-memory buffer and a second accumulator. gpudims masks the store to lidx0==0, and a barrier separates the shared store from the shared loads.
  • Names list one number per axis: globals, locals/group-reduces, upcasts, reduces, unrolls.
  • MAX starts at −∞ and becomes compare + select (FSETP/FSEL in SASS).
  • PyTorch eager uses one templated reduce_kernel. Inductor picks persistent (per) or looped (red) Triton kernels and reduces within a warp with shuffles.
